## (2) 指摘

### 指摘 1
- **perspective**: P1
- **対象**: [docs/nfr/nfr-grade.md:103](<repo>/docs/nfr/nfr-grade.md:103)、[docs/adr/_review-summary.md:85](<repo>/docs/adr/_review-summary.md:85)
- **severity**: high
- **claim**: 既存の表計算ファイルから先の予約を移さず、社員に予約し直してもらう方針には、利用開始前の照合が組み込まれていない。
- **evidence**: NFR はデータを変換せず社員が予約し直すと定める。ADR の確認事項は「予約し直しが済んだことを確かめる手順が無い」と明記している。原文は二重予約の解消を求めている。
- **why_raised**: 切替時に予約し直されない枠があると、新システムでは空きとして別の社員が予約できる。中心要求の二重予約防止が、利用開始時点で破れる。
- **suggested_fix**: 切替前に旧ファイルの更新を止め、将来の予約を移行または再登録して全件照合した後に利用を開始する手順を決定に含める。

### 指摘 2
- **perspective**: P1
- **対象**: [docs/adr/0007-testing-strategy.md:33](<repo>/docs/adr/0007-testing-strategy.md:33)、[docs/rules/testing.md:53](<repo>/docs/rules/testing.md:53)
- **severity**: medium
- **claim**: Web 画面での表示と操作を求める要求に対し、受入を API ドライバで実行し、ブラウザでは確認しない方針になっている。
- **evidence**: 原文は社員が空き状況を Web 画面で見て予約・取消することを求める。ADR 0007 はブラウザ受入を行わず、画面のボタンと API の結線誤りを受入では見つけられないと記している。
- **why_raised**: API が正しくても、画面から予約や取消を実行できない状態で受入が通り得る。社員が使う主要な経路の成立を確認できない。
- **suggested_fix**: 少なくとも照会・予約・取消の代表経路を、ブラウザから通す受入確認に加える。
