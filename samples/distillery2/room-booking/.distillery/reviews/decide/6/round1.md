## (2) 指摘

### 指摘 1
- **perspective**: P2
- **対象**: `docs/nfr/nfr-grade.md:43,75`、`docs/adr/0016-backup-point-in-time-recovery.md:34-38,56`、`docs/rules/tier-backend.md:99-103`
- **severity**: high
- **claim**: 復旧地点の有効な決定が成果物内で矛盾している。非機能グレードは「前日の最終バックアップまで」、ADR 0016 と rules は「障害の直前まで」と定める。
- **evidence**: 非機能グレードの A.4.1.1 は前日までの復旧、C.1.2.1 は日次バックアップを指定する。ADR 0016 はその案を却下し、同期した更新記録による障害直前への復旧を決定している。ADR 自身も 56 行目で不一致が残ると明記する。
- **why_raised**: 障害当日に成立を通知した予約が日次バックアップからの復旧で消えると、別の社員が同じ枠を予約できる。要求の二重予約防止に関わり、実装者が参照する文書によって復旧方式も変わる。
- **suggested_fix**: 非機能グレードの RPO とバックアップ方式を ADR 0016 に合わせ、Markdown と YAML の両方を更新する。

### 指摘 2
- **perspective**: P3
- **対象**: `docs/adr/0015-api-access-token-jwt.md:29,51`、`docs/adr/_review-summary.md:73-82`
- **severity**: medium
- **claim**: 社内認証基盤が API 向けの JWT アクセストークンを発行できるかという未確認の前提が、確認事項に載っていない。
- **evidence**: ADR 0015 は JWT、社員 ID を含む `sub`、API 向けの `aud` を前提とし、満たせなければ ADR の置き換えが必要と記す。一方、確認事項の認証に関する問いは OIDC ログインの可否だけである。
- **why_raised**: 認証基盤が OIDC ログインには対応していても、指定した形式のアクセストークンを発行できない場合、現行の API 検証方式では利用者が予約機能を使えない。方式変更の判断が必要な前提である。
- **suggested_fix**: JWT 形式、`sub`、API 向け `aud`、公開鍵による検証の可否を確認事項に加える。
