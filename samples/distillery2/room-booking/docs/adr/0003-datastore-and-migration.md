# 背景

情報は「会議室」(5 部屋の固定データ) と「予約」(状態「予約済み / 取消済み」を持つ) の 2 つで、量は小さい。要求は「同じ会議室の同じ時間帯は二重に予約できない。同時に予約されても成立するのは 1 件だけ」と定め、時刻は 30 分刻みに限られる。会議室の登録画面は作らず、初期データで入れると決まっている。テストは pglite (接続が 1 つの埋め込み DB) で回す。

# 決定

- データストアは PostgreSQL 互換の RDB 1 つにする。ベンダーのサービスは選ばない。テストは pglite で同じ migration を当てる。
- スキーマは migration ファイルで管理する (表の形は段階③の DB 契約で決める)。会議室 5 部屋は migration の初期データにする。
- 二重予約は DB の一意制約で防ぐ。時刻が 30 分刻みなので、予約が占める 30 分枠を 1 行ずつ「会議室の 30 分枠の占有」の表に書き、(会議室 ID, 枠の開始時刻) に一意制約を付ける。10:00-11:00 の予約は 10:00 と 10:30 の 2 行を占める。終了と次の開始が同じ予約 (10:00-11:00 と 11:00-12:00) は枠が重ならないので両方成立する。取り消すと占有の行を消すので、同じ枠をまた予約できる。
- 同時に 2 人が同じ枠を予約したとき、後に書いた側のトランザクションが一意制約で失敗し、「時間帯が重なる」と返る。
- 日時は UTC で保存し、日付と 30 分刻みは業務のタイムゾーン (Asia/Tokyo) で判定する。

# 却下した案

- 範囲の排他制約 (時間帯の範囲が重ならない制約): PostgreSQL では会議室 ID の等しさと組み合わせるのに拡張 (btree_gist) が要る。pglite でその拡張を読み込めるかを確かめていない。また 30 分刻みの枠なら普通の一意制約で同じことが守れる。
- アプリで重なりを確かめてから書く (行ロックで直列化): 一意制約が無いと、確認と書き込みの間に別の予約が入りうる。pglite は接続が 1 つで同時実行を再現できず、ロックの正しさをテストで確かめられない。
- キャッシュ・全文検索・ファイル置き場を足す: 頻繁に参照される重いマスタも、画像も、検索も無い。

# 影響

- 二重予約の防止が DB の制約になり、同時の予約でも 1 件だけが成立する。この決まりは DB 契約のテストで確かめられる。
- 予約 1 件で占有の行が枠の数だけ増える (1 時間の予約で 2 行)。数十人の規模では問題にならない。
- 刻みを 30 分から変えると占有の表を作り直す必要がある (刻みを変える要求が出たら、この ADR を置き換える)。
