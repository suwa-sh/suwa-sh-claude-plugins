# 背景

要求に通知・メール・集計・一括処理・定期処理は無く、状態遷移にタイマー起動も無い。外部システムも無い。予約と取り消しは画面の操作に対してその場で結果を返す必要がある。

# 決定

- メッセージングは不要とする。すべての UC を同期の要求と応答で完結させる。
- 冪等キー (Idempotency-Key) も入れない。予約を二重に送っても 2 件目は「時間帯が重なる」で成立せず、取り消しを二重に送っても 2 件目は「取り消せない」で受け付けられない。業務のルールが重複の副作用を防ぐ。
- 画面では送信中のボタンを押せなくして、二重の送信そのものを減らす。

# 却下した案

- 非同期のメッセージで予約を処理する: 予約の成否をその場で返す必要があり、遅延を許せない。
- 冪等キーを入れる: 二重の送信は業務のルールで既に弾かれる。キーの保存の仕組みが増えるだけ。

# 影響

- worker と AsyncAPI の契約が要らず、構成が単純になる。
- 二重に送った予約は「重なる」エラーとして返るため、画面ではそれを利用者に分かる文で表示する。
- 通知 (予約の確認メールなど) が後から要るときは、メッセージングの ADR を新しく書く。
