# 背景

運用では、予約が成立しなかった理由や取り消しの事実を後から追えるとよい (非機能グレードのログ種別)。ログの保管は 3 ヶ月の仮置きで、監査ログは予約のイベントの表が代わりを担う。情報「予約」は社員の識別子だけを持ち、氏名や連絡先は持たない。

# 決定

- 形は JSON の 1 行 (pino で出す)。標準出力に出し、保管は実行環境に任せる。
- 必ず持つ項目: 時刻・レベル・メッセージ・相関 ID・ハンドラの名前。社員が分かる要求では社員 ID (トークンの sub。個人情報でない識別子)。
- レベル: error = システムのエラー / warn = 外部とのやり取りの一時的な失敗 / info = 要求の始まりと終わり・業務のイベント / debug = 開発のときだけ。
- 層ごと: presentation = 要求の始まりと終わり / usecase = 業務のイベント / gateway = 外部の失敗 / domain = 出さない。
- 出さないもの: トークン・鍵・要求と応答の本文の全体。

# 却下した案

- テキストのログ: 運用で相関 ID や UC で検索・集計しにくい。
- domain でもログを出す: domain の純粋さ (外部ライブラリに依存しない) が崩れる。
- 監査用のログを別に作る: 予約と取り消しの事実はイベントの表に残る。

# 影響

- テストの計装 (実行トレース) とは別の仕組みになる。ログは運用のため、計装はテストと実装の記録のため。
- 保管の期間 (3 ヶ月の仮置き) は実行環境の設定で決める。
