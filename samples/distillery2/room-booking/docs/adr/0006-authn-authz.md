# 背景

予約には予約者を記録し、取り消せるのは予約者本人だけ (条件「予約の取消可否」)、自分の予約の一覧には他の社員の予約を出さない。そのため社員を見分ける必要がある。要求の段で「社内の既存アカウントでログインする」を仮置きした (社内の認証の仕組みの詳細はまだ確認していない)。アクターは社員 1 種でロールの違いは無い。空き状況の画面では予約者の名前を出さないと決まっている。

# 決定

- 認証は社内の既存アカウントの認証基盤に OIDC (OpenID Connect) で任せる (Federated Identity)。frontend は認証基盤からトークンを得て、API を呼ぶときに付ける。backend-api はトークンを検証して社員の識別子 (sub) を得る。
- 認可のモデルは、ロールを持たない所有者の判定だけにする。取り消しと一覧は「予約者 = 要求した社員」を domain で判定する。開始時刻を過ぎた・取消済みの判定は認可ではなく domain の業務のルールで扱う。
- 空き状況は誰でも (ログインした社員なら) 見られるが、予約者は返さない。

# 却下した案

- このシステム専用の ID とパスワードを作る: パスワードを保持する責任が増え、社員はアカウントが 1 つ増える。要求の段で既存のアカウントを使うと仮置きした。
- ロールベース (RBAC) や外部の認可サービス: ロールが無く、所有者の判定 1 種だけでは過剰。
- 認可サービスを置く: 判定は予約者の一致 1 つだけ。

# 影響

- 社内の認証基盤が OIDC に対応していることが前提になる。対応していなければ認証の方式を置き換える ADR が要る (確認してほしいこと)。
- テストでは実際の認証基盤を使わず、テスト用の検証器でトークンの社員を決める。
- 認証基盤の設定 (発行者・クライアント ID) は環境ごとの設定にする。
