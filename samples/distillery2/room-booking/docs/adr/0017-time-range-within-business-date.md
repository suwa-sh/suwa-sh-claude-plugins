# 背景

要求の差し戻しで、条件「予約時刻の妥当性」の時間帯の形の検査に「開始と終了は指定した日付の中に収める (終了は翌日 0:00 まで可。日をまたぐ時間帯は不可)」が足され、空き状況の照会と予約の両方で使うと決まった (受入基準: 23:30-翌日 0:00 は受け付け、23:00-翌日 1:00 は時間帯が正しくないとして受け付けない)。

課題 `docs/feedback/20261104_202116_precheck_precheck-view-room-availability-backend_time-range-within-day-decision.md` (空き状況の照会の着手前の確認から出た課題で、`from_uc` は無い) で、決定が古い要求のままだと分かった。

- ADR 0009 の時間帯の値オブジェクトの検証は「開始が終了より前・30 分刻み」の 2 つだけで、日付に収まることを含まない。
- ADR 0010 のコード表は INVALID_TIME_RANGE を「開始が終了より前でない」とだけ定め、日付に収まらないときのコードが無い。
- 時間帯が属する日付を何で決めるかと、終了の 24:00 をどう持つかが決まっていない。

時間帯は値オブジェクトの 1 か所で検証する (ADR 0009) ため、ここで決めた扱いが予約・取り消し・一覧の UC にもそのまま効く。ADR 0009 と 0010 は置き換えず、そのまま有効とし、時間帯の検証とコードの意味をこの ADR で足す。

# 決定

- 時間帯の値オブジェクトは生成のときに 3 つを検証する: 開始 < 終了、30 分刻み、業務の日付の 0:00 から翌日 0:00 までに収まる。検証の順はこの順とし、最初に満たさないもののコードを返す (どの UC でも同じ入力に同じコードを返す)。
- 業務の日付は、開始の日時の Asia/Tokyo の日付で決める。要求で日付を別の項目として受け、時間帯と突き合わせることはしない (契約の時間帯の形 `TimeRange` は開始と終了の日時だけを持つ)。
- 終了の 24:00 は翌日 0:00 の日時として持つ。日時は RFC 3339 (24 時の表記を持たない) で受け、UTC で保存する。占有の表 (ADR 0003) では 23:30 の枠がその日の最後の枠になる。
- 日付に収まらない時間帯は INVALID_TIME_RANGE (422) に含める。ADR 0010 のコード表の INVALID_TIME_RANGE の意味は「開始が終了より前でない、または時間帯が業務の日付の中に収まらない」と読む。
- 過去でないことの検査は予約の集約の作成のメソッドだけに置き、照会では使わない。

| コード | 意味 (この ADR の後) | status |
|---|---|---|
| INVALID_TIME_RANGE | 開始が終了より前でない、または時間帯が業務の日付 (開始の日付・日本時間) の 0:00 から翌日 0:00 までに収まらない | 422 |
| NOT_ON_30_MINUTES | 30 分刻みでない (変更なし) | 422 |
| PAST_TIME_SLOT | 開始が現在より前 (予約のときだけ。変更なし) | 422 |

# 却下した案

- 日付に収まらないことに新しいコード (例: 日をまたぐ時間帯) を作る: 受入基準は逆転・同じ時刻と同じ「時間帯が正しくない」で示す。画面の文を分ける理由が無く、コードと画面の文が増えるだけになる。
- 業務の日付を要求の別の項目 (日付) で受ける: 日付と開始の日時の 2 か所に日付があり、食い違ったときの扱いをさらに決める必要がある。予約の要求は開始と終了の日時だけで足りる。
- 終了の 24:00 を「24:00」という時刻の表記で持つ: RFC 3339 の日時でも日付の計算でも扱えず、変換の場所が増える。
- 日をまたぐ時間帯を許す: 要求の条件 (日をまたぐ時間帯は不可) に反する。

# 影響

- 契約の段で、`ErrorCode` の説明と `responses.UnprocessableEntity` の説明に「時間帯が業務の日付の中に収まらない」を足す (INVALID_TIME_RANGE と同じ意味にする)。コードの列挙は変わらない。
- 画面の INVALID_TIME_RANGE の文は「時間帯が正しくない」ことを示す文に直す (今の「終了時刻は開始時刻より後に」は日をまたぐ時間帯に当てはまらない)。
- 時間帯の検証は domain の単体テストで確かめる (23:30-翌日 0:00 は作れる、23:00-翌日 1:00 は INVALID_TIME_RANGE)。
- 開発ルール (docs/rules/) は作り直しが要る (この ADR の受理後に行う)。アーキテストの規則は増えない (層とティアの依存は変えない)。
