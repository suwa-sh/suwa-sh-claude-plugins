# 背景

空き状況の照会の UC (`from_uc: view-room-availability`) の独立検証の課題 (`docs/feedback/20261104_231524_verify_findings.frontend_token-expiry-unknown.md`) で、次の穴が見つかった。

- ADR 0019 は、保存したトークンの期限 (expires_in) が 60 秒より長いか、60 秒以下か切れているかで「そのまま返す」「更新して返す」「サインインへ戻す」を分ける。
- 認証基盤が expires_in を返さないとき (OAuth 2.0 では返すことが推奨で、必須ではない) の扱いを決めていない。OIDC クライアント (oidc-client-ts) は、そのとき expires_at と expires_in を undefined にする。
- 実装者は「更新せずにそのまま使い、API が 401 を返したらサインインへ戻す」と補った (実装者の前提の記録 A-019、`apps/frontend/src/api/oidcTokenProvider.ts`)。

ADR 0019 の決定は変えずにそのまま有効とし、この ADR で期限の分からないときの扱いを足す。

# 決定

- 期限の分からないトークンは、期限が近くないものとしてそのまま返す。更新もサインインへの送り出しもしない。
- 期限が実際に切れていれば、API が 401 を返す (ADR 0015 の検証器が exp を確かめる)。画面は ADR 0014 の 401 の扱いと ADR 0018 の戻り先のとおりサインインへ戻す。この場合のための仕組みは足さない。
- 画面はアクセストークン (JWT) の中身を読んで期限を求めない。
- トークンの供給元の単体テストに「期限が無い」の組み合わせを足す。

# 却下した案

- 期限が分からなければ使う前に毎回更新する: リフレッシュトークンがあれば、API を呼ぶたびに更新の往復が増え、ローテーションするリフレッシュトークンを毎回使い捨てる。リフレッシュトークンが無いと ADR 0019 の「サインインへ戻す」に当たり、戻ってきたトークンにも期限が無いので、API を呼ぶたびにサインインへ戻り続ける。
- 画面がアクセストークン (JWT) の exp を読んで期限を求める: アクセストークンは本来 API (backend-api) が検証する値で、画面にとっては中身の分からない値である。画面に JWT を読む部品と判断が増え、ADR 0015 が API に置いた検証と役割が重なる。
- 決まった長さ (例: 5 分) の期限を仮に置く: 認証基盤の実際の設定と合わず、短すぎれば不要な更新が増え、長すぎれば結局 401 で戻るので得るものが無い。

# 影響

- トークンの供給元の本番の実装に「期限が無い」の分岐が 1 つ加わる。今の実装 (A-019) のとおりで、作り直しは要らない。
- 認証基盤が expires_in を返さないと、期限前の画面の裏の更新は効かず、期限が切れたあとの最初の API の呼び出しで 401 になってサインインへ戻る。入力中の値は戻らない (ADR 0018 のとおり)。リフレッシュトークンがあっても、期限前の更新は働かない。返すかどうかで画面の動きは決まっている (どちらでもサインインへ戻れる) が、利用者への影響 (予約の入力中に期限が切れると入力し直す) の頻度は認証基盤の設定で変わる。このため確信度を低くし、認証基盤の登録のときに次の 2 点を確かめる (ADR 0019 のリフレッシュトークンの確認と同じ時期)。
  - 認証基盤がトークンの応答で expires_in を返すか。
  - 返さない場合に、期限ごとのサインインへの戻りと入力値の消失を許容するか。許容しなければ、expires_in を返すよう認証基盤を設定するか、この決定を見直す。
- 開発ルール (docs/rules/) はこの ADR から生成し直す (ADR を直すたびに d2-run が行う)。アーキテストの規則は増えない (層とティアの依存は変えない)。
