# 背景

情報「予約」は状態「予約済み → 取消済み」を持つ。取り消された予約は空き状況と重なりの判定から外れるが、誰がいつ予約し、いつ取り消したかは後から説明できるほうがよい (表計算ファイルで「取り消しが反映されない」問題があった)。情報「会議室」は 5 部屋の固定データで、履歴は要らない。

# 決定

- 一部イミュータブルにする。業務の事実 (予約した・取り消した) は予約のイベントの表に追記だけで残す。
- 今の状態は予約の表 (予約 ID・会議室・開始・終了・予約者・予約状態) に別に持ち、イベントと同じトランザクションで更新する。照会・一覧・重なりの判定はこの表と占有の表 (データストアの決定を参照) を読む。
- 取り消しは行を消さず、取り消しのイベントを足して状態を取消済みにする。
- 会議室は上書きのマスタにする。
- イベントは起きた時刻と行為者を持つ。記録した時刻は DB の既定値で付ける。

# 却下した案

- 上書きだけ (予約の行の状態を書き換えるだけ): 取り消した時刻と人が残らない。
- イベントだけ持ち、今の状態を毎回イベントから求める (イベントソーシング): 状態は 2 つだけで監査の規制も無い。照会のたびに求めるのは手間に見合わない。
- 会議室も履歴を持つ: 会議室を変える機能が無い。

# 影響

- 予約と取り消しの記録が消えずに残り、監査ログの代わりになる。
- 予約の今の状態の表は更新されるので、イベントの表と食い違わないよう、両方を同じトランザクションで書く必要がある。
