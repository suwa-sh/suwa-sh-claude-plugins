# 背景

ADR 0005 を置き換える。会議室を予約する UC (`from_uc: reserve-room`) の契約の段で出た課題 (`docs/feedback/20261110_015840_contract_contract-20261110T015344Z_adr-0005-resend-rationale.md`) で、次の食い違いが見つかった。

- ADR 0005 の「決定」は、冪等キーを入れない理由を「予約を二重に送っても 2 件目は時間帯が重なるで成立しない」としている。
- ADR 0005 の「影響」は「二重に送った予約は重なるエラーとして返るため、画面ではそれを利用者に分かる文で表示する」としている。
- 要求の SPEC-002-03 は、自分の有効な予約と会議室・日付・開始時刻・終了時刻がすべて同じ予約をもう一度送ったときは、新しい予約を作らず、成立済みの予約を予約が成立した結果として示すと決めている (応答が届かなかったときの送り直し)。

この理由と影響の文は要求と両立しない。冪等キーを入れない決定と、ADR 0005 の rules (同期で完結・送信中のボタンを押せなくする) は変えなくてよい。ADR は本文を書き換えずに履歴を残す決まりのため、ADR 0005 を置き換え、その rules 2 本を文面を変えずに引き継ぐ。

あわせて、送り直しを冪等キーではなく予約の内容で判定することを rules に 1 本足す。ADR 0005 の「冪等キーを入れない」は本文にしか無く、rules が無いため、送り直しを実装するときにキーの保存を足す余地が残っていた。

ティア構成・データストア・依存のパッケージは変えない。

# 決定

- メッセージングは不要とする。すべての UC を同期の要求と応答で完結させる (ADR 0005 のとおり)。
- 冪等キー (Idempotency-Key) は入れない。重複の副作用は業務のルールで防ぐ。
  - 同じ社員が、自分の有効な予約と会議室・開始・終了がすべて同じ予約を送り直したときは、新しい予約を作らず、成立済みの予約を予約が成立した結果として返す (SPEC-002-03)。
  - それ以外の重複 (時間帯が一部だけ重なる自分の予約・他の社員の予約と重なる予約) は「時間帯が重なる」で成立しない。
  - 取り消しを二重に送っても、2 件目は「すでに取り消された予約」で受け付けない (SPEC-003-02)。
- 送り直しの判定は、送った社員の有効な予約を会議室・開始・終了で探して行う。キーや要求の識別子は保存しない。
- 送り直しの判定は、過去の時間帯の判定より先に行う (SPEC-002-03)。処理の順は次のとおり。
  1. 入力の時間帯を値オブジェクトで検証する (開始が終了より前・30 分刻み・日付の中に収まる。ADR 0017)。
  2. 送った社員の有効な予約に、会議室・開始・終了がすべて同じものを探す。
  3. あれば、過去の時間帯の判定・重なりの判定・新規作成を行わず、その予約を予約が成立した結果として返す。現在が開始時刻や終了時刻を過ぎていても同じ。
  4. 無ければ、予約の集約を作り (ここで過去の時間帯を検査する。ADR 0017)、重なりを判定する。取り消した自分の予約と同じ内容は 2 で見つからないので、ここで新しい予約として扱い、開始を過ぎていれば過去の時間帯として受け付けない。
- 過去の時間帯の検査を予約の集約の作成だけに置く ADR 0017 の決定は変えない。送り直しは集約を作る前に返すので、その検査を通らない。
- 画面では送信中のボタンを押せなくして、二重の送信そのものを減らす (ADR 0005 のとおり)。

# 却下した案

- 非同期のメッセージで予約を処理する: 予約の成否をその場で返す必要があり、遅延を許せない (ADR 0005 のとおり)。
- 予約の集約を作ってから (過去の時間帯の検査の後に) 送り直しを探す: 応答が届かずに開始時刻を過ぎてから送り直すと、過去の時間帯として断られ、成立済みの予約を確かめられない (SPEC-002-03 の受入基準 5 に反する)。
- 冪等キーを入れる: 送り直しは予約の内容 (本人・会議室・時間帯) で見分けられ、要求が決める範囲 (自分の有効な予約と同じ内容) と一致する。キーの保存と期限切れの後始末の仕組みが増えるだけ。
- ADR 0005 を有効のまま残し、この ADR で理由だけを補う: ADR 0005 の「影響」の「二重に送った予約は重なるエラーとして返る」が有効な決定として残り、画面の担当が送り直しを重なるエラーとして表示しうる。

# 影響

- ADR 0005 は置き換え済み (superseded) になり、その rules はこの ADR から開発ルールに入る。
- ADR 0005 の影響のうち「二重に送った予約は重なるエラーとして返る」は無くなる。送り直した予約は予約が成立した結果として返るので、画面は通常の成立と同じ表示をする (重なるエラーの文は、本当に重なったときだけ出す)。
- 予約の API は、成立済みの予約を返す応答を契約に持つ (応答の形は契約の段で決める)。
- worker と AsyncAPI の契約が要らず、構成が単純になる (ADR 0005 のとおり)。
- 通知 (予約の確認メールなど) が後から要るときは、メッセージングの ADR を新しく書く (ADR 0005 のとおり)。
- 開発ルール (docs/rules/ の common・tier-frontend・tier-backend) はこの ADR の受理後に作り直す。アーキテストの規則は増えない (層とティアの依存は変えない)。
