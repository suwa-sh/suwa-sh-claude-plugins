# 背景

決定の段の第三者レビューの後の引き継ぎ (課題 `docs/feedback/20261104_133050_decide_decide-refute-20261104T132848Z_rpo-restore-double-booking.md`。UC からではなく決定の段から出た課題で `from_uc` は無い) で、次の穴が見つかった。

- 非機能グレード表は、目標復旧地点 (A.4.1.1) を「前日の最終バックアップまで」、バックアップ (C.1.2.1) を日次としている。
- この場合、障害の日に成立した予約と取り消しが復旧で消える。ADR 0003 の占有の表も同じく戻るので、利用者に成立を知らせた枠を別の社員が予約でき、要求の「同じ会議室の同じ時間帯は二重に予約できない」(SPEC-002-02) が復旧の後に破れる。

目標復旧地点は「障害の直前まで戻す」と決めた (人への確認の推奨で決定済み)。ADR 0003 はデータストアと二重予約の防止の決定であり、バックアップの仕方は決めていない。ADR 0003 は置き換えず、そのまま有効とし、バックアップと復旧の決まりをこの ADR で足す。

# 決定

- 目標復旧地点を障害の直前にする。DB のバックアップは、定期のフルバックアップに加えて、更新の記録 (トランザクションログ) を絶えず DB とは別の保管場所へ残す。復旧はフルバックアップに更新の記録を当てて、障害の直前の時点まで戻す。
- 守る障害の範囲は「DB 本体 (サーバとその記憶装置) を失う障害」とし、この範囲で許すデータの損失は無し (利用者に知らせた予約と取り消しを 1 件も失わない) とする。
- そのため、更新の記録は別の保管場所へ同期して書き、別の保管場所への書き込みの完了を確かめてから確定 (コミット) を完了とする。別の保管場所へ届かないときは、予約の成立と取り消しを受け付けずに失敗を返す (知らせた後に失う予約を作らない)。
- 予約の成立と取り消しの応答は、この確定の完了の後に返す。利用者に知らせた結果は、必ず別の保管場所の更新の記録に入っている。
- 誤操作の取り消しなどで障害の直前より前の時点へ意図して戻す復旧は、この保証の範囲の外とする。その場合は、利用を再開する前に、戻した時点の後に成立を知らせた予約を更新の記録から洗い出す。
- 予約の表と占有の表は同じ DB にあり (ADR 0003)、復旧では同じ時点へ戻す。占有の表だけを別に戻さない。
- 復旧の後、利用を再開する前に、占有の行が予約済みの予約の枠と一致することを確かめる。
- 製品・サービスは選ばない (ベンダーニュートラル)。PostgreSQL 互換の RDB (ADR 0003) が持つ更新の記録の保管と時点を指定した復旧の仕組みで満たす。

# 却下した案

- 前日の最終バックアップまでの復旧 (日次バックアップだけ): 障害の日の予約と取り消しが消え、成立を知らせた枠を別の社員が予約できる。二重予約の防止 (SPEC-002-02) が復旧の後に破れる。
- バックアップの間隔を短くする (1 時間ごとのフルなど): 間隔の分だけ予約が消える穴は残り、二重予約の防止を守れない。
- 復旧の後に、消えた予約を利用者の申告で入れ直す: 申告の漏れと重なりを確かめる手作業が要り、確実でない。
- 更新の記録を別の保管場所へ非同期に送る (確定の後に送る): 確定から送り終わるまでの間に DB 本体を失うと、成立を知らせた予約が戻せず、二重予約の防止が破れる。

# 影響

- 更新の記録を残す保管場所と、その保管の量が増える (予約の量は小さく、負担は小さい)。
- 予約の成立と取り消しの応答は、別の保管場所への書き込みを待つ分だけ遅くなる。別の保管場所が止まっている間は、予約の成立と取り消しができない (空き状況の参照はできる)。二重予約の防止を可用性より優先する。
- 非機能グレード表の A.4.1.1 (前日の最終バックアップまで) と C.1.2.1 (日次) は、この決定と食い違ったままになる。グレード表はこの段の差分の書き込み範囲の外であり、直す道は既にある課題 (グレード表を直す道が決定の差分に無い件) で扱う。グレード表を直すときは A.4.1.1 を障害の直前まで、C.1.2.1 に更新の記録を別の保管場所へ同期して残すことを書く。
- 開発ルール (docs/rules/) とアーキテスト (.dependency-cruiser.cjs) は作り直しが要る (この ADR の受理後に行う)。アーキテストの規則は増えない (層とティアの依存は変えない)。
