# 背景

書籍・貸出・予約は状態モデルを持ち、貸出と予約を失うと誰が何を借りているかと予約順位が分からなくなる (NFR A.4.1.1 Lv3)。
利用者は氏名と連絡先 (個人情報) を持つ (NFR E.6.1.1)。
既存データは紙台帳と表計算ファイルにあり、量は小さい (NFR D.4.1.1 Lv1)。

# 決定

- データストアは単一の RDB にする。所有者は backend-api (ADR 0001)。
- エンティティを次のように分類する。

  | 情報 | 分類 | 理由 |
  |---|---|---|
  | 書籍 | event_snapshot | 書籍状態を持つ |
  | 貸出 | event_snapshot | 貸出状態を持ち、延滞の記録を残す |
  | 予約 | event_snapshot | 予約状態と予約順位を持つ |
  | 通知 | event | 送信の記録で、登録後に変えない |
  | 利用者 | resource_mutable (論理削除) | 状態モデルが無い単純なマスタ |
  | 在庫状況レポート・人気書籍ランキング・貸出統計 | 保存しない | 貸出と書籍から都度集計する |

- 媒体種別と通知種別は区分値として持ち、追加できるようにする (将来の電子書籍対応)。
- 書籍検索は RDB の検索機能で行い、専用の検索エンジンは置かない。
- スキーマは migration ファイルで管理する。DDL は段階③で DB 契約から作り、テストでは pglite で検証する。
- 紙台帳と表計算ファイルからの移行は、本番開始前に書籍と利用者を一括で取り込む。取り込み前に重複と表記ゆれを整理する。

# 却下した案

- すべてのエンティティを Event Sourcing にする案: 規制による完全履歴の要件が無く、状態遷移も 8 種未満のため過剰になる。
- 利用者も event_snapshot にする案: 連絡先の変更履歴を追う要件が無い。
- 全文検索エンジンを追加する案: 単館の蔵書規模 (NFR B.1.1.2) では RDB の検索で足り、運用対象が増える。
- レポートを集計テーブルに保存する案: 同時アクセスが小さく、集計の鮮度管理の手間が上回る。

# 影響

- 貸出と予約の変化が追記で残るため、障害直前までの復旧 (NFR A.4.1.1) と延滞の追跡がしやすい。
- repository が events と snapshot の二重書き込みを 1 トランザクションで隠す必要がある。
- 取り込み用の移行スクリプトが本番開始前に 1 回だけ要る。
