# 背景

情報は 10 種あり、そのうち 4 種 (蔵書・貸出・予約・通知) が状態モデルを持つ。
条件の多く (貸出可否・予約順位付与・督促重複抑止など) が複数の情報をまたいで状態を参照する。
貸出・予約の記録は失うと窓口で再現できないため、RPO は数時間前まで (A.4.1.1 Lv2) とした。
移行元は紙台帳と表計算ファイルで、データ量は小さい (D.4.1.1 Lv1)。

# 決定

- ストレージは単一の RDB (PostgreSQL 互換) にする。キャッシュ・全文検索エンジン・オブジェクトストレージは置かない。
- 情報ごとの保持方式は次のとおりにする。

  | 情報 | 保持方式 | 理由 |
  |---|---|---|
  | 蔵書 | 履歴+スナップショット | 書籍の状態 (在庫あり・貸出中・取り置き中・除籍済み) を持つ |
  | 貸出 | 履歴+スナップショット | 貸出の状態 (貸出中・延滞中・返却済み) を持ち、貸出統計の元データになる |
  | 予約 | 履歴+スナップショット | 予約の状態と予約順位の繰り上げを持つ |
  | 通知 | 履歴+スナップショット | 通知の状態 (送信待ち・送信済み) を持ち、重複送信の判定に使う |
  | 貸出ルール | 適用開始日つきの世代管理 | 属性「適用開始日」を持ち、過去の貸出の返却期限を説明できる必要がある |
  | 書籍・利用者・司書 | 更新可能なマスタ (論理削除) | 状態モデルを持たない |
  | 在庫状況・貸出統計 | 保存しない (問い合わせ時に集計) | 他の情報から導出でき、1 館規模なら集計が軽い |

- 検索 (キーワード・タイトル・著者・ISBN・ジャンル) は RDB の索引と部分一致で行う。
- スキーマは migration ファイルで管理する。DB 契約は段階③で定め、テストでは組み込み型の PostgreSQL 互換 DB (pglite) で検証する。
- 紙台帳と表計算ファイルからの初期データは、稼働前に取込スクリプトで一括移行する (D.2.1.1 Lv1)。取込時に入力チェック (タイトル必須・メール形式・ISBN の重複) を適用する。

# 却下した案

- すべての情報をイベントソーシングにする案: 金融・医療のような監査要件が無く、状態遷移も 8 種未満のため過剰である。
- 全文検索エンジンを併設する案: 1 館の蔵書数なら RDB の検索で応答 5 秒以内 (B.2.1.1 Lv3) を満たせる。
- 在庫状況・貸出統計を集計テーブルとして保存する案: 更新のたびに整合を取る必要が生じる。集計が重くなった時点で読み取り用の集計を追加すればよい。
- 利用者を履歴+スナップショットにする案: 退会後も個人情報の履歴が残り続け、個人情報保護の観点で扱いにくい。

# 影響

- 利点: 蔵書・貸出・予約の状態変化を後から追跡でき、窓口の問い合わせや移行後の照合に使える。
- 利点: 単一 RDB のため、返却と取り置きと通知の登録を 1 トランザクションで確定できる (ADR 0005)。
- 欠点: 状態を持つ情報は履歴とスナップショットの二重書き込みになる。repository が 1 トランザクションで隠す。
- 欠点: 利用者の退会は論理削除のため、個人情報の消去期限は運用で別途決める必要がある。
