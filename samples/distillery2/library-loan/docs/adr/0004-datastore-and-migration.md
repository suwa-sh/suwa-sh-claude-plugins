# 背景

- 情報は 6 つ (書籍・利用者・貸出・予約・通知・貸出統計) ある。このうち 5 つが状態モデルを持ち、外部キーで互いに結び付く。
- 予約順の繰り上げ、返却時の取置、延滞判定は、複数の情報の状態を一緒に変える。
- 情報「利用者」は個人情報を持つ (NFR E.6.1.1)。貸出統計は貸出の記録から集計できる。
- 書籍の検索はタイトル・著者への部分一致で足り、1 館規模では専用の検索エンジンは要らない。

# 決定

- ストレージは単一の RDB (PostgreSQL 互換) とする。キャッシュ・オブジェクトストレージ・検索エンジンは置かない。
- 情報の分類は次のとおりとする。
  - 書籍・利用者・貸出・予約・通知: 状態を持つため、イベント (追記のみ) と現在状態のスナップショットで記録する。
  - 貸出統計: 保存せず、貸出の記録から要求時に集計する。
- 削除は削除済み状態への遷移で表す。
- 同じ書籍への同時操作は、書籍単位の版番号による楽観ロックで直列化する。
- スキーマは migration ファイルで管理する。migration は backend-api だけが持つ (ADR-0001 の datastore_owner)。DDL は段階③で DB 契約から生成する。
- 紙台帳と表計算ファイルからの初期移行は、移行用の取り込み処理が書籍・利用者の登録イベントを作る形で行う。

# 却下した案

- すべての情報を上書き更新のテーブルで持つ: 予約順や延滞の経緯を後から追えず、通知の送信結果も残らないため却下。
- 全面的なイベントソーシング (スナップショットを持たずイベント再生で状態を作る): 金融・医療のような監査規制が無く、過剰なため却下。
- 貸出統計を集計テーブルに保存する: 1 館規模では要求時の集計で間に合い、集計ずれの管理が要らなくなるため却下。
- 全文検索エンジンを併用する: 部分一致検索で要件を満たせるため却下。

# 影響

- 良い点: 貸出・予約・通知の経緯をすべて追える。障害直前までの復旧 (NFR A.4.1.1) もしやすい。
- 悪い点: 書き込みのたびにイベントとスナップショットの 2 つを書く必要がある。
- 注意点: 削除済みの利用者も個人情報がイベントに残る。保存期間と匿名化の方針は運用で決める必要がある (確認事項)。
