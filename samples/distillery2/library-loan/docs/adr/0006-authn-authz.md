# 背景

- 社外アクター「利用者」がインターネットから Web 画面にログインする。社内アクター「司書」は管理操作を行う。
- 条件「操作権限条件」はロールによる制御を求める。条件「利用状況閲覧範囲条件」は、本人の貸出と予約だけを見せることを求める。
- 情報「利用者」は個人情報を持つ (NFR E.1.2.1)。データ感度が高いため、ロールだけでなく本人確認 (所有者の属性) による認可が要る。

# 決定

- 認証: OIDC 準拠の IdP に委ねる (Federated Identity)。IdP はマネージドでもセルフホストでもよい。製品は段階③以降で選ぶ。
  - 利用者: ID とパスワード、およびパスワードポリシー (NFR E.5.1.1 Lv2)
  - 司書: 多要素認証を推奨する
- 認可: ロール (司書 / 利用者) と本人確認 (利用者番号の一致) を、backend-api の usecase 層で判定する。外部のポリシーエンジンや認可サービスは置かない。
- 状態による可否 (有効な利用者か、延滞中でないか) は認可ではなく、domain 層のビジネスルールとして扱う。
- 利用者向けと司書向けのフロントは別の OIDC クライアントとし、セッションを共有しない。司書向けは館内ネットワークからの接続に限る運用を推奨する (NFR E.5.3.1、仮置き)。

# 却下した案

- アプリ内の自前 ID とパスワードの認証: パスワードの保管と漏えい対策を自前で持つことになり、個人情報を扱う一般向けサービスには不向きなため却下。ただし 1 館規模では IdP の運用負担が重い可能性があるため、確認事項とする。
- 外部のポリシーエンジンや関係ベースの認可サービス: 所有者と条件のパターンが少なく (本人確認とロールだけ)、過剰なため却下。
- ロールだけの認可: 利用者が他人の貸出履歴を見られてしまうため却下。

# 影響

- 良い点: アプリがパスワードを持たずに済み、認可の判定箇所が usecase 層に集まる。
- 悪い点: IdP の導入と運用 (利用者アカウントの発行・パスワード再設定) が必要になる。
- 残る課題: 利用者を登録したときに IdP のアカウントを発行する連携方法は、段階③以降で決める。
