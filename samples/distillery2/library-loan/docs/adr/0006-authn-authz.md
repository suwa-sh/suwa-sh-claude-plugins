# 背景

アクターは司書 (社内) と利用者 (社外) の 2 種。
利用者は Web 画面で自分の貸出履歴と予約状況を見る。他の利用者の貸出は表示しない (SPEC-006-01)。
利用者情報は氏名と連絡先を含む個人情報で、個人情報保護法に準拠する (NFR E.1.2.1)。

# 決定

- 認証は OIDC 準拠の IdP に委ねる (Federated Identity)。
  - 司書と利用者は同じ IdP を使い、ロールをトークンのクレームで区別する。
  - IdP をマネージドにするかセルフホストにするかはインフラ選定で決める (ベンダーニュートラル)。
  - パスワードポリシーは IdP 側で設定する (NFR E.5.1.1 Lv2)。
- 利用者のアカウントは司書が利用者を登録するときに作り、IdP の主体と利用者番号を対応付ける。
- 認可はロール (司書 / 利用者) と所有者チェック (本人の利用者番号) の組み合わせで行う。
  - 判定は backend-api の usecase 層で行う。外部の認可サービスやポリシーエンジンは置かない。
  - 状態による可否 (貸出中の書籍は削除できない等) は認可ではなく domain の業務ルールで判定する。
- 個人情報へのアクセスは監査ログに残す (NFR E.7.1.1 Lv2)。

# 却下した案

- アプリ内で ID とパスワードを管理する簡易認証: 社外の利用者のパスワードを保持する責任と漏えいリスクをアプリが負う。
- 司書と利用者で別の IdP を使う案: 社内ディレクトリ連携の要件が無く、運用対象が増える。
- ポリシーエンジンや関係ベース認可 (ReBAC) の外部サービス: 所有者パターンは「本人の貸出・予約」だけで、条件も少なく過剰になる。
- ロールだけで判定する案 (RBAC のみ): 個人情報を扱うため、利用者同士のデータ分離を所有者チェックで保証する必要がある。

# 影響

- アプリはパスワードを保持せず、トークン検証だけを実装すればよい。
- テストでは IdP を差し替えられるよう、トークン検証をポートインターフェイス越しにする。
- 利用者のアカウント発行手順 (司書の登録時に IdP に作る) は要求に記述が無いため、確認が要る。
