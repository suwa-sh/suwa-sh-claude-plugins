# 背景

- アクターは利用者と司書の 2 種で、権限と導線が大きく異なる。
  - 利用者: 検索・予約・自分の利用状況
  - 司書: 蔵書と利用者の管理、カウンター業務、レポート
- 両者は同じ書籍情報と状態 (在庫あり・貸出中・予約待ちなど) を表示するため、見た目を揃えたい。
- 利用者は一般の図書館利用者で、スマートフォンからの利用やアクセシビリティへの配慮が見込まれる (NFR F.1.1.3 / F.3.1.2、いずれも仮置き)。

# 決定

- フロントを 2 本に分ける。
  - 利用者向け: `frontend-patron`
  - 司書向け: `frontend-staff`
- 共通の UI 部品と design tokens を packages/ui に持つ。部品の生成は後段の段階 (デザイン) が担う。
- 書籍・貸出・予約の状態の表示は packages/ui の共通定義に揃える。
- 多言語対応はしない (要求に無い)。

# 却下した案

- 単一のフロントで利用者向けと司書向けを画面ごとに出し分ける: アプリの数は減るが、司書機能を館内ネットワークに限る制御や、権限ごとの導線の分離が難しくなるため却下。規模の小ささを優先するなら有力な代替案として確認対象とする。
- 共通部品を持たず画面ごとに直接実装する: 2 本のフロントで状態表示や書籍カードが二重実装になり、見た目がずれるため却下。
- 利用者向け・司書向けに加えて BFF を置く: フロントは 2 種で UI 要件の差を API 側で吸収する必要が無いため却下。

# 影響

- 良い点: 利用者と司書の画面を独立して改修できる。共通部品で見た目とアクセシビリティを揃えられる。
- 悪い点: フロントのビルドとデプロイが 2 本になる。packages/ui の保守が加わる。
