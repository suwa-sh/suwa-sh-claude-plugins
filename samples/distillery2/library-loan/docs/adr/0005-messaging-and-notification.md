# 背景

RDRA のイベントは 3 つ (受取可能メール送信依頼・返却期限リマインドメール送信依頼・延滞督促メール送信依頼) で、送り先はすべて外部システム「メール配信サービス」である。
同じイベントを複数の業務が購読する関係は無い。
条件「督促重複抑止」は、同じ延滞に同じ日に督促メールを重複送信しないことを求める。
返却登録の応答を、メール配信サービスの遅延や障害で止めてはならない。

# 決定

- メッセージキューは置かない。AsyncAPI 契約も作らない。
- 通知は「送信待ち」の通知レコードとして、業務更新と同じトランザクションで RDB に記録する (トランザクショナル outbox)。
  - 受取可能通知: 返却登録で予約が取り置き中になった時点で記録する。
  - 返却期限リマインド・延滞督促: 日次ジョブが対象を判定して記録する。
- 送信待ちの通知は、worker が数分ごとに起動する送信ジョブが backend-api 経由で送る。成功したら送信済みにする。失敗したら送信待ちのまま残し、次回に再送する。
- 同日の重複送信は、通知種別・対象・送信日の一意制約で防ぐ。
- 更新 API に冪等キーのヘッダは設けない。二重予約は業務上の一意制約 (同じ利用者・同じ書籍の有効な予約は 1 件) で防ぐ。

# 却下した案

- メッセージキュー + 購読 worker 案: 購読者が常に 1 つで、1 館の通知件数も少ない。キューの運用コストに見合わない。
- 返却登録の処理中にメールを同期送信する案: メール配信サービスの障害で返却登録が失敗する。送信の成否も記録できない。
- 更新 API すべてに冪等キーを必須にする案: 金銭取引が無い。重複の害は業務上の一意制約で防げる範囲に収まる。

# 影響

- 利点: 業務更新と通知の記録が必ず一致し、通知漏れ (受取可能・督促) を防げる。
- 利点: 通知の状態がそのまま送信履歴になり、同日の重複判定に使える。
- 欠点: 受取可能メールは返却登録の直後ではなく、送信ジョブの間隔 (数分) だけ遅れて届く。
- 欠点: 送信失敗が続くと送信待ちが溜まる。アプリケーション監視 (C.1.3.1 Lv3) で滞留件数を見張る必要がある。
