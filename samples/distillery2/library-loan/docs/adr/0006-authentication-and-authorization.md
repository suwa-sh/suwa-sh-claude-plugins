# 背景

社外アクター「利用者」と社内アクター「司書」が、どちらも Web 画面にログインして使う。
条件「操作権限」は利用者区分で機能を出し分ける。条件「本人情報参照制限」は、利用者に自分の貸出・予約だけを見せる。
情報「利用者」は氏名とメールアドレスの個人情報を持つ。
NFR はパスワードポリシー付きの認証 (E.5.1.1 Lv2) と RBAC (E.5.2.1 Lv2) を仮置きした。

# 決定

- 認証は OIDC 準拠の外部の認証基盤に委ねる (Federated Identity)。利用者と司書で同じ認証基盤を使う。
  - frontend は認可コードフロー (PKCE) でログインする。
  - backend-api はアクセストークンを検証し、認証基盤の主体 ID をアプリ内の利用者または司書に対応づける。
  - パスワードとパスワードポリシーは認証基盤が持つ。アプリはパスワードを保持しない。
  - マネージド型にするかセルフホスト型にするかは、インフラ段階で決める。
  - テストでは、テスト用のトークン発行器に差し替える。
- 認可は backend-api の中で行い、独立した認可サービスは置かない。
  - ロールによる判定: 利用者区分 (司書 / 利用者) で操作を許可する。
  - 本人所有による判定: 利用者が参照・取消できるのは、本人の利用者番号に一致する貸出・予約だけにする。
  - 状態による判定 (貸出可否・予約可否・削除可否): 認可ではなく domain の業務ルールで判定する。
- 司書が利用者を登録するとき、認証基盤にもアカウントを作る。認証基盤との連携はゲートウェイのポート越しに行う。

# 却下した案

- アプリ内で ID とパスワードを管理する簡易認証案: 社外の利用者のパスワードをアプリが保持することになり、漏えい時の影響が大きい。
- 利用者向けと司書向けで認証基盤を分ける案: 認証経路を分ける要求が無い (E.5.3.1)。frontend を 1 つにした決定 (ADR 0001) と合わない。
- ポリシーエンジンや関係ベースの認可サービスを置く案: 所有権の判定は「本人の利用者番号か」の 1 種類だけで、外部サービスの導入に見合わない。

# 影響

- 利点: パスワードをアプリで持たず、多要素認証が必要になっても認証基盤側の設定で追加できる。
- 利点: 認可が usecase 層に集まり、「他人の貸出が見えない」ことを単体テストで確かめられる。
- 欠点: 利用者登録の UC が認証基盤へのアカウント作成を含み、失敗時の整合 (片方だけ作られる) を扱う必要がある。
- 欠点: 認証基盤の種類が未定のため、ログイン UC の結合確認はテスト用トークン発行器での確認に留まる。
