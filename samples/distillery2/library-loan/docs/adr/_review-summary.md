# 決定段階のレビュー要約 (図書館蔵書管理システム)

この段階では、次の 2 つを決めました。

- システムに求める品質の水準 (非機能要求グレード表)
- 作り方の大きな方針 (8 件の決定記録)

いずれも推奨案を自動で採用しています。根拠の弱い項目は、下の「確認してほしいこと」に挙げました。

## 1. 品質の水準 (非機能要求グレード表)

### 前提

- 想定規模: 「社会的影響が限定される一般向けサービス」を採用しました。
  - 根拠 1: 一般の図書館利用者がインターネットから使います。
  - 根拠 2: お金・医療・行政のデータは扱いません。
  - 根拠 3: まずは 1 館で運用します。
- 処理量と性能の水準は、1 館の規模に合わせて標準より低めにしました。
- 全 97 項目に水準を付けました。そのうち 44 項目が重要項目です。

### 主な水準

| 観点 | 決めた水準 | 根拠 |
|---|---|---|
| 稼働時間 | 夜間も概ね動かす (1 時間程度の停止あり) | 利用者が Web で予約・確認する。日次の期限チェックがある |
| 障害時の復旧 | 障害直前の状態まで、2 時間以内に戻す | 貸出と予約の順番を失うと公平性が崩れる |
| 同時アクセス | 100 以下 | 1 館での運用 |
| 画面の応答 | 5 秒以内 | 一般利用者向けの画面操作が多い |
| 日次の期限チェック | 翌開館前 (8 時間以内) に終える | リマインドと督促を毎日作る |
| バックアップ | 毎日 (フル+差分) | 情報の項目数が多い |
| 監視 | アプリの動きまで監視する | 通知の送信失敗を見逃さない |
| 法令 | 個人情報保護法に対応する | 利用者の氏名・住所・電話番号・貸出履歴を持つ |
| アクセス制御 | 役割 (司書 / 利用者) と本人確認で制御する | 利用者は自分の貸出と予約だけを見られる |
| 暗号化 | 通信はすべて暗号化する。個人情報は保管時も暗号化する | 個人情報とインターネット経由の通信がある |
| 監査ログ | ログインと個人データへのアクセスを記録する | 司書が利用者情報を管理する |
| 拡張性 | 媒体の種類を足すだけで電子書籍に広げられる構成 | 将来の電子書籍対応の要望 |

## 3. 確認してほしいこと

### 確信度が低い決定 (選択肢)

1. **画面を 2 本に分けるか (決定 1・8)**
   - ⭐採用: 利用者向けと司書向けの 2 本に分ける。
     - 利点: 導線と権限を独立させやすい。
     - 利点: 司書画面を館内ネットワークに限りやすい。
   - 代替: 1 本の画面アプリで、ログインした役割に応じて出し分ける。
     - 利点: ビルドと公開の手間が半分になる。
     - 利点: 1 館の小規模運用には軽い。
2. **ログインの仕組み (決定 6)**
   - ⭐採用: 外部の認証サービス (OIDC 対応) に任せる。
     - 利点: アプリがパスワードを持たずに済む。
     - 利点: 司書の二段階認証も載せやすい。
   - 代替: アプリ内で ID とパスワードを管理する簡易認証。
     - 利点: 認証サービスの導入と運用が要らない。
     - 欠点: パスワードの保管と漏えい対策を自前で持つ。
3. **言語と骨組み (決定 2)**
   - ⭐採用: すべて TypeScript で書く。API の骨組みは次の段階で選ぶ。
   - 代替: 開発チームが慣れた別の言語をサーバ側に使う。
     - 欠点: 型の共有と既定のテスト基盤が使えなくなる。

### 仮置きした品質水準

上の「根拠が弱く仮置きした重要項目」の表を確認してください。とくに次の 3 点は、今後の構成とコストに効きます。

- 運用体制: 開館時間内に開発チームが兼務する、で良いか。
- 災害対策: 遠隔地へのバックアップ保管だけで良いか。
- ログの保管期間: 個人情報へのアクセス記録を 3 か月で良いか。

### そのほかの注意点

- 削除済みの利用者も、個人情報が出来事の記録に残ります。保存期間と匿名化の方針を決める必要があります。
- 司書向け画面を館内ネットワークに限る運用も、仮置きです。
- 次の 2 点も仮置きです。
  - 利用者のスマートフォン利用
  - アクセシビリティの目標水準
