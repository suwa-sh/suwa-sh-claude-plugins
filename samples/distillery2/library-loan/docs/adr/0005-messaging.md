# 背景

- 非同期で処理するのは 3 種類の通知 (取置通知・返却期限リマインド・延滞督促) と、日次の期限チェックだけである。
- 情報「通知」は送信待ち・送信済み・送信失敗の状態を持つ。送信失敗は再送できる (条件「通知送信条件」)。
- 通知を受け取るのは worker 1 つだけで、複数の業務が同じイベントを購読することは無い。

# 決定

- メッセージブローカーは置かない。AsyncAPI 契約は作らない。
- 情報「通知」を送信待ちレコード (outbox) として使う。
  - 返却の登録で取置が決まったとき、backend-api は同じトランザクションで送信待ちの取置通知を作る。
  - 日次の期限チェックでは、worker が backend-api の usecase を呼び、送信待ちのリマインドと督促を作る。
- worker は短い間隔 (数分ごと) で送信待ちの通知を読み、メール配信サービスへ送る。結果を送信済みまたは送信失敗として記録する。
- 冪等性を次の手段で保つ。
  - DB の一意制約
  - 通知 ID 単位の送信
  - 利用者の更新系 API の Idempotency-Key
- この決定の背景には、社外アクター「利用者」によるリトライ重複のリスクと、予約という更新系の業務がある。

# 却下した案

- メッセージブローカーを置き、非同期メッセージで通知を配る: 購読者が 1 つで、1 館規模の通知件数ではブローカーの運用コストに見合わないため却下。
- 返却の登録時に backend-api がその場でメールを送る: メール配信サービスが遅いと返却登録も遅れ、送信失敗で業務の更新が巻き戻るおそれがあるため却下。

# 影響

- 良い点: 業務の更新と通知の作成が必ず一致する。送信失敗も記録されて再送できる。
- 悪い点: 取置通知の送信は worker の実行間隔 (数分) だけ遅れる。
- 将来の拡張: 分館の追加などで購読者が増えたら、メッセージブローカーの導入をこの ADR の置き換えとして検討する。
