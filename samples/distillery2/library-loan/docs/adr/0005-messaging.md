# 背景

返却通知・リマインド・督促の 3 種のメールを外部システム「メール配信システム」経由で送る。
返却通知は返却登録を契機に、リマインドと督促はタイマー「日次期限チェック」を契機に送る。
メールの購読者は 1 つで、複数業務が同じイベントを消費する構成は無い。
社外の利用者は予約を再送する恐れがあり、窓口の貸出・返却も二重登録を防ぐ必要がある。

# 決定

- メッセージブローカーは置かず、AsyncAPI 契約も作らない。
- 通知は outbox 方式で送る。
  - backend-api は業務の更新と同じトランザクションで「通知」を送信待ちとして記録する。
  - worker が定期的に backend-api の送信ジョブを起動し、送信待ちの通知をメール配信システムへ送る。
  - 送信結果は通知に追記する (ADR 0004)。
- 日次期限チェックは worker が 1 日 1 回 backend-api のジョブを起動する。対象日を指定し、再実行しても重複送信しない。
- 更新系 API は Idempotency-Key で再送を吸収する。

# 却下した案

- メッセージキューとイベント駆動の worker を置く案: 購読者が 1 つで、遅延も数分単位で許容できるため、運用対象が増えるだけになる。
- 返却登録の処理中にメールを同期送信する案: メール配信システムの障害で返却登録が失敗するか、送信が抜ける。
- Idempotency-Key を使わない案: 社外の利用者の再送と窓口の二重クリックで、予約や貸出が重複する。

# 影響

- 返却登録とメール送信の依頼が必ず一致し、連絡漏れを防げる。
- メール送信は数分遅れる。返却通知は即時性が求められていないため許容する。
- 送信失敗は通知の記録から検知でき、監視 (NFR C.1.3.1 Lv3) の対象にする。
