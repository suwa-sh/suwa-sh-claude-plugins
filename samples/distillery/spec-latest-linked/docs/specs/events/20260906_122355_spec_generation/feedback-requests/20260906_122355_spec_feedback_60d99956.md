## CR-60d99956-001: 貸出期間の日数と利用者区分対応をRDRAで定義する

- severity: spec-gap
- related_ids: [RDRA-LOAN-PERIOD]
- related_files: [docs/rdra/latest/条件.tsv, docs/rdra/latest/バリエーション.tsv]

### 観測した事実

条件の返却期限設定条件は日数加算を要求する。バリエーションは利用者区分と貸出期間区分の名前のみで、日数・対応表がない。designページStoryには独自の固定日数と一般利用者の長期制限がある。

### 現在の仕様と問題

貸出期限と利用可能な期間区分を追加判断なしに計算できない。Storyのサンプル値を業務条件に転用すると正本が分散する。

### 変更してほしいこと

次の表を返却期限設定条件とバリエーションへ採用する。

| 期間区分 | 日数 | 利用者区分 |
|---|---|---|
| 標準 | 14暦日 | 一般、学生、団体 |
| 短期 | 7暦日 | 一般、学生、団体 |
| 長期 | 30暦日 | 学生、団体 |

画面の初期選択は標準とする。APIは期間区分を必須にし、一般の長期指定は409 LOAN_PERIOD_NOT_ALLOWEDで拒否する。
貸出日は処理開始時のAsia/Tokyo暦日とし、日数を加算した日を期限とする。休日調整は行わない。
この日数と一般の長期制限は現行ページStoryを根拠に選んだ未採用の提案であり、現行RDRAの確定値ではない。

### 完了条件

貸出登録と貸出可否照会の期限計算・分岐・BDD、および窓口ページStoryが同じRDRA条件を参照して一意に決まる。

## CR-60d99956-002: 予約待ちと取置き対象者の貸出条件の優先順位を確定する

- severity: spec-gap
- related_ids: [RDRA-LOAN-ELIGIBILITY]
- related_files: [docs/rdra/latest/条件.tsv, docs/rdra/latest/状態.tsv]

### 観測した事実

貸出可否条件は予約待ちを拒否する一方、取置き中書籍貸出条件は対象者を許可し、状態.tsvにも予約待ちからの貸出遷移が存在する。

### 現在の仕様と問題

同一入力に許可と拒否の両方が適用できる。

### 変更してほしいこと

利用者が利用可能かつ紙書籍であることを共通前提とし、次の順序で判定する。

1. 取置き中予約があれば、予約順1位で要求利用者と一致する1件だけを貸出対象とする。書籍状態は予約待ちであることを要求する。この例外を予約待ちの一般的な拒否より優先する。
2. 取置き中予約がなければ、在庫ありの書籍だけを許可する。
3. 取置き対象者不一致、予約待ちで取置きなし、貸出中、同順位の取置きが複数、電子書籍は409 BOOK_NOT_LOANABLEで拒否する。

対象予約は貸出済みへ更新し、後続の有効予約順位を繰り上げる。取置き期限の経過だけでは状態を推測せず、予約取消工程が確定した状態を使う。

### 完了条件

予約待ちの対象者/非対象者で分岐が一意に決まり、登録・可否照会・予約参照のシーケンスとBDDを再検証できる。

## CR-60d99956-003: 利用可能と利用者状態の対応を確定する

- severity: spec-gap
- related_ids: [RDRA-USER-STATE]
- related_files: [docs/rdra/latest/条件.tsv, docs/rdra/latest/状態.tsv]

### 観測した事実

貸出可否条件は利用者状態区分「利用可能」を要求する。状態.tsvの利用者状態は登録済みと取引進行中であり利用可能はない。

### 現在の仕様と問題

登録済みだけか、取引進行中も貸出可能かを決められない。

### 変更してほしいこと

「利用可能」を登録済みまたは取引進行中の利用者と定義する。既存取引の存在だけでは追加貸出を拒否しない。
登録済みからの貸出は取引進行中へ遷移し、取引進行中からの貸出は同状態を維持する遷移を状態.tsvへ追加する。
利用者が存在しない場合は404、定義された利用可能状態でない場合は409 USER_NOT_LOANABLEとする。

### 完了条件

登録と可否照会が全利用者状態に対して一意の結果を返せ、利用者状態遷移とBDDが矛盾しない。

## CR-60d99956-004: SubmitActionButtonの送信責任を実装と説明で揃える

- severity: spec-gap

- related_files: [docs/design/latest/storybook-app/src/components/common/SubmitActionButton.tsx, docs/design/latest/storybook-app/src/stories/forms/SubmitActionButton.stories.tsx]

コメントとStory説明から部品自身がHTTPヘッダを送る記述を除き、callback責務へ揃える。クリックだけで部品内部が自動的にsubmittingを変更する説明も除く。

### 完了条件

## CR-60d99956-006: DB確定後のKVS障害に対する冪等応答回復を確定する

- severity: spec-gap
- related_ids: [ARCH-SR-013, ARCH-SR-025, ARCH-CTP-006]
- related_files: [docs/arch/latest/arch-design.md]

### 観測した事実

SR-013はKVSへ冪等キーを記録して前回応答を返す。SR-025はRDBの冪等列UNIQUEを要求する。両ストアの途中障害時の前回応答復元は記述されていない。

### 現在の仕様と問題

RDB commit後KVS記録前の停止で重複防止と同じ応答再送を両立する永続データ・照合順序が未定義である。

### 変更してほしいこと

次の回復方式をSR-013、SR-025、CTP-006へ採用する。

| 項目 | 具体案 |
|---|---|
| キー | UUIDv7。74乱数bitは暗号学的乱数で生成し、埋込Unixミリ秒を発行時刻とする |
| 互換性 | この新契約は従来UUIDv4を受理しない。画面/APIを同時切替し、既存v4未確定操作は旧版回復経路で確認してから移行する |
| 時刻検証 | 認証認可と型検証後、発行時刻がサーバー現在より5分超未来なら400 INVALID_REQUEST |
| 期限 | 発行時刻+24時間。現在時刻が期限以上なら、DBレコードの有無にかかわらず410 IDEMPOTENCY_KEY_EXPIRED |
| 照合範囲 | 認証主体ID、operationId、キーの一意組 |
| 保存元 | 業務更新と同一RDB取引でrequest_hash、response_status、response_body、response_location、expires_atを保存 |
| hash | 検証済みbook_id、user_no、loan_period_typeをその順のコンパクトJSON、UTF-8、SHA-256 |
| KVS | RDBreceiptの複製を期限までキャッシュ。取得失敗時はRDBへfallback |
| 同一キー | 本文不一致409 IDEMPOTENCY_KEY_CONFLICT。進行中409 IDEMPOTENCY_KEY_IN_PROGRESS。完了は初回201本文とLocationを返す |
| 清掃 | 期限以降にreceiptとキャッシュを削除できる。期限判定を先に行うため削除後も同じキーを再実行しない |
| 画面 | キーと本文を認証主体別sessionStorageへ保存後に送信。応答不明時は保持し、再読込後も同じ組で再試行 |
| 期限外回復 | 自動再送と新キー発行を停止し、司書による貸出記録の確認後にだけ入力を再開 |

同一RDB取引の最初にreceipt仮行（応答3列NULL）をINSERTしてキーを確保する。UNIQUE競合の待機上限は100ミリ秒で、超過はrollbackと409 IDEMPOTENCY_KEY_IN_PROGRESS。既存行の一意違反はrollback後にreceiptを再照合する。業務更新後に応答3列をUPDATEし、未完了の仮行はcommitしない。
認証失効と権限不足でも結果不明の要求を保持し、同じ認証主体の認証回復後に同じキーで照合する。ログアウト時も要求を保持し、他主体へ引き継がない。タブ閉鎖で保存要求を失った場合は司書の記録確認を必須とする。

commit後KVS保存前の停止でもRDBから応答を復元する。RDBへ到達できなければ503とし、未成功と断定しない。
これは本提案で選択した24時間保証であり、現行architectureに原子的receipt方式が既にあるという意味ではない。

### 完了条件

貸出登録・その他更新UCのモデル/契約/画面再送が同じ回復規則を参照し、commit前後およびKVS障害の受入条件が決まる。

## CR-60d99956-007: 貸出画面の利用者カードを取得可能なデータに接続する

- related_ids: [DESIGN-LOAN-USER-CARD]
- related_files: [docs/design/latest/storybook-app/src/components/domain/UserProfileCard.tsx, docs/design/latest/storybook-app/src/stories/Pages/司書ポータル/窓口貸出受付画面.stories.tsx]

### 観測した事実

UserProfileCardはemailとregisteredAtを必須に持ち、窓口ページは固定値を渡す。現在の照会契約LoanTargetResponseはuser_no,name,user_category,user_status,loanableであり両項目を返さない。

### 完了条件
