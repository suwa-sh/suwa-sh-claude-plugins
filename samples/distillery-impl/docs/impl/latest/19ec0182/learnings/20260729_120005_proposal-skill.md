# skill/機構への提案(採否はユーザー判断。このファイル自体は既存ファイルを編集していない)

## 提案1: S0 bootstrap の scaffold テンプレートに ts-node の module オーバーライドを標準で含める

- **対象ファイル**: distillery-impl の bootstrap(P3_skeleton)が生成する各tierの `tsconfig.json`
  テンプレート、または dist-impl-run の scaffold 手順を記述したドキュメント
  (`skills/dist-impl-run/` 配下、または bootstrap を担う skill の references)。
- **現状の記述**: `tsconfig.json` は `../tsconfig.base.json`(`"module": "ESNext"`)を extends する
  のみで、`ts-node`(cucumber-js の step definition 実行に使用)向けの CommonJS オーバーライドを
  含まない。
- **提案する変更**: scaffold テンプレートの `tsconfig.json` に、以下の `ts-node` オーバーライドを
  標準で含める。

  ```jsonc
  {
    "extends": "../tsconfig.base.json",
    "ts-node": {
      "compilerOptions": { "module": "CommonJS" }
    }
  }
  ```

- **根拠となった出来事**: `module: ESNext` + `ts-node/register` + `cucumber-js` の組み合わせでは、
  step definition からローカルTSファイルへ拡張子なし相対importを追加した瞬間にモジュール解決エラーが
  発生する(詳細: `learnings/20260729_120002_tsnode_esm_relative_import_resolution.md`)。本UCの
  tier-frontend でこの問題を踏み Context7でts-node公式ドキュメントを調べて解決したが、同じ
  scaffold パターンを使う tier-backend-api / tier-worker、および他UCの全tierが同じ調査を
  繰り返す可能性が高い。scaffold時点で標準搭載しておけば、この既知の踏み抜きを事前に防げる。

## 提案2: impl-config.yaml のフレームワーク依存確定を、S0/S3で全tier一括install する運用に明文化する

- **対象ファイル**: `skills/dist-impl-run/references/state-schema.md`(または同等の
  S0 bootstrap / S3 contracts の手順書)。
- **現状の記述**: `impl-config.yaml` の `backend_framework` 等はユーザー確定値として記録されるが、
  その依存(`express` 等)を「いつ・誰が」`package.json`/共有ロックファイルに反映するかの手順が
  明記されていない。
- **提案する変更**: S0 bootstrap または S3(共有セットアップ)の時点で、`impl-config.yaml` の
  各tier `commands`/`backend_framework` 等から要求される依存を洗い出し、単一writerとして
  一括で `package.json` に追加・`npm install` まで完了させる工程を追加する。
- **根拠となった出来事**: tier-backend-api の write-set が `backend-api/` 配下に隔離されている
  一方、npm workspacesは単一の共有ロックファイルを使うため、S4(tier並走)の時点で新規依存を
  追加しようとすると write-set分離との衝突(かつ他tierの並走Implementerとの競合リスク)が生じる
  (詳細: `learnings/20260729_120001_express_dependency_single_writer_constraint.md`)。
  本UCではattempt-1で`node:http`による暫定実装→attempt-2でオーケストレータが依存追加、という
  2 attempt分のコストがかかった。
