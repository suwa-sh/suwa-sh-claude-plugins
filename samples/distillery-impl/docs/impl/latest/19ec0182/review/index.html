業務フロー (BUC)
貸出管理フロー — 貸出管理業務の中の「貸す」側の流れ（対になる「返す」流れは別UC「書籍を返却する」）
ユースケース (UC)
書籍を貸出する — 本レビューの対象。1回の貸出手続きの開始から完了までの単位

この実装では、貸出という1つのユースケースを2つのtierに分けて作っています。

tier役割主な実装物
tier-frontend 貸出手続き画面の表示とAPI呼び出し LoanConfirmationScreen（画面）/ LoanConfirmationPage（ルート層）/ LoanConfirmationApiClient
tier-backend-api 貸出可否判定・貸出期限計算・在庫状態遷移・予約整合性チェック POST /api/v1/loans, GET /api/v1/books/:id / createLoanUseCase / loans・books・reservations テーブル操作

処理の要旨: 利用者が蔵書検索画面から貸出ボタンを押す →「在庫あり・予約なし」の条件を満たせば貸出を確定し、書籍の状態を「在庫あり」から「貸出中」に変更、返却期限（貸出日+14日）を計算して画面に表示する。予約者本人による貸出の場合は、対応する予約レコードも「完了」に更新する。

残る2件のmajorは以下のとおり、いずれも「仕様に契約が存在しない」ことが根本原因であり、frontend・backend双方とも独立にVerifierから同一の指摘を受けています（3者独立検出）。

  • 認証スタブ（backend, security major）: 仕様はOAuth2/OIDC認証を要求するが、認証基盤自体が実装環境に提供されていない。X-User-Idヘッダの値をそのまま信用するスタブ実装で代替。
  • X-User-Idハーネス注入（frontend, security major = F-004）: frontendのAPIクライアントはX-User-Idヘッダを一切送信しない契約（仕様上そもそも定義がない）。S6/S7の統合テストはテストコード側でこのヘッダを注入して通しており、本番の画面操作導線では届かない。

承認する場合・差し戻す場合それぞれで何が確定するか

承認すると確定すること

  1. UC「書籍を貸出する」の実装（frontend・backend-api）が本番相当のコードとして確定する。6段ゲートは全てpass、open blockerは0件
  2. 認証スタブ・X-User-Idハーネス注入の2件のmajorは「実装の欠陥」ではなく「仕様の欠落」として扱われ、本UCの実装をやり直す対象からは外れる。是正はdistillery側の仕様修正 → 次サイクルでの再実装に委ねられる
  3. 11件の変更要求がdistilleryへの正式なインプットとして確定し、次の仕様生成サイクルの対象になる

差し戻す場合に戻る先

  1. 「認証・X-User-Id契約を仕様確定させてから実装をやり直したい」場合 → S8で起票済みの変更要求（認証契約・reservations仕様）をdistilleryで先に処理し、本UCをS1（uc-init）からやり直す
  2. 「本番導線でもX-User-Idが届くようにfrontendだけ直したい」場合 → S4 tier-frontendへ差し戻し、LoanConfirmationApiClientにヘッダ送信を追加する（ただし現仕様にヘッダ契約自体が無いため、暫定対応になる点に留意）
