# 実装対象を説明する仕様の書き方

## 本文の読者と対象

spec.mdとtier仕様の読者は実装者と受入担当者とする。
本文には、還流要求の具体案が採用された場合のシステムの振る舞いを記述する。
概要にはアクター、契機、達成する結果、対象範囲を1〜3文で示す。

| 情報 | 記録先 |
|---|---|
| UCの目的、分岐、観測可能な結果 | spec.md |
| 入出力の接続、処理順序、状態の所有者、障害時の結果 | tier仕様 |
| 型と制約 | 分割API契約または分割RDB schema |
| 生成状態、未採用の提案、実行記録、参照の基準パス | イベントのREADMEまたはレビュー記録 |
| 現在の正本との差分、具体的な変更案、完了条件 | feedback-requestsの変更要求 |
| 提案と本文の対応、採用状況、照合結果 | _review/proposal-baseline.md |

スキルの手順、distilleryの実行状況、本文の編集禁止や省略方針は生成対象の仕様本文へ出力しない。
本文の参照は「[条件](latestへのリンク)の条件名を参照する」の形とする。
「ここには書かない」「再掲しない」「未確定のため実装できない」などの編集上の説明は本文から除く。
プロダクトの動作を規定する「失敗時は更新しない」等の否定は必要な仕様として残す。

## テクニカルライティング

利用可能なjapanese-tech-writingスキルを読み、その文章規範を適用する。
利用できない環境でも次の規範を生成とレビューへ適用する。
ユーザーの「表やリストで構造を伝える」という指定を段落主体の一般指針より優先する。

| 伝える内容 | 表現 |
|---|---|
| 目的と設計理由 | 短い文章。一文一行。一段落一論点 |
| 並列の条件と結果 | 条件、処理、結果の対応表 |
| 時間順の処理 | 番号付きリスト |
| 並行処理、通信、取引境界、入れ子の分岐 | シーケンス図 |
| データの移動 | データフロー図 |
| 所有者と値の受け渡し | 入力元、受取先、変換、更新契機の表 |
| 有限の選択肢と適用対象 | 箇条書き |
| 具体的な受入結果 | Given/When/Then |

- 主語、対象、条件、結果を特定し、同じ概念には同じ用語を使う。
- 図や表を文章で言い換えて繰り返さない。
- 大きな表は判断の単位で分ける。セルに複数段落を詰め込まない。
- 見出しは対象や判断を特定する自然な句にする。
- 空の強調や予告、姿勢の表明、冗長な但し書きを除く。
- 原子性、競合、再送、結果不明、日付境界など、実装結果を変える条件は保持する。

## 具体案と採用状況

上流への変更要求は、採用後の意味が一意に決まる具体案にする。
「日数を決める」「整合させる」だけで完了する要求にしない。
既存の実装例から値を選ぶ場合は、提案の根拠として記録し、承認済みの正本とは区別する。

1. 現在のlatestと不足を確認する。
2. 値、条件の優先順位、Props、保持期間などの具体案を変更要求に記録する。
3. その具体案を採用した場合の本文を生成する。
4. _review/proposal-baseline.mdへ要求ID、参照対象、提案内容の所在、対応する本文やBDD、採用状況を記録する。
5. 未採用の具体案がある出力はイベントとして保存し、本文外のreadinessをneeds-spec-changeとする。

本文の業務条件や部品契約は引き続きlatestを参照する。
現時点のlatestと提案内容の差はproposal-baselineに記録する。
本文で仮定の注釈を繰り返さず、イベント入口のREADMEとレビュー画面で提案を含む出力であることを表示する。

## 還流後の整合確認

spec工程は最新の正本と提案の基準を照合する。
同じ案が採用された場合は、本文を再生成せず整合確認の結果を記録する。

| 照合結果 | spec工程の処理 | 本文 |
|---|---|---|
| 提案どおり採用され、参照先と契約が整合する | 新しいlatestを実際に読み、分岐、契約、BDDを確認する | 維持する |
| 別案が採用され、結果が変わる | 影響する箇所を特定して差分を修正する | 必要箇所のみ変更する |
| 未採用、一部採用、参照先欠落、矛盾がある | 未解決の内容と所有工程を記録する | 採用済みと扱わない |

実際に照合したファイルと内容、判定、本文の変更有無をレビュー記録に残す。
ファイルが存在するだけ、またはhashが更新されただけでは意味の整合を確認したことにしない。
全提案の採用と実装可能性を確認してからlatestへ昇格する。
既存イベントの本文は変更せず、新しいイベントに必要な照合結果を記録する。
受信したpipeline packetのdispositionやledgerは従来の実測契約に従い、本文を維持しただけで上流要求をappliedにしない。

本文の意味を維持することと、pipelineのno-change判定は別に扱う。
初めてlatestへ昇格する場合は、本文が同じでもsnapshotが変わるため通常の昇格処理と実測ledgerを用いる。
昇格時の相対リンク補正は位置変更に伴う機械処理として記録し、仕様内容の再設計と区別する。

## 本文検査

新規生成したUCへ `validateSpecProse.js <UC-directory>` を実行する。
このlintはCR番号、生成状態、編集上の指示の典型例だけを検出する。
技術的な否定条件、画面の未確定状態、latestの参照は許容する。
文の意味、提案の採用状態、表の正しさは独立レビューで確認する。
