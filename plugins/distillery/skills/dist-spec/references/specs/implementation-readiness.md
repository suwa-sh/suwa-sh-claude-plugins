# 実装可能性を基準にした出力

> 新規生成は `references/specs/latest-linked-spec.md` を優先する。業務条件・状態遷移はRDRA latest、部品契約はdesign latestのStorybookへ参照し、再定義しない。分割OpenAPIを直接編集し、不足はpipelineへ還流する。

目的は、実装者が業務上の挙動を発明せずに実装し、正誤を検証できる仕様を出すこと。
生成モデル・実行CLI・既存出力の再現性は、この判定の条件にしない。
legacy / catalog の両方に適用する。構文検証、契約の機械生成、既存BDDの保持だけでは合格にならない。

## 残す情報と置き場所

| 実装時の判断 | 正本 | 必要な内容 |
|---|---|---|
| 何を成立させるか | RDRA latest + UC本文の接続 | 対象・アクター・業務条件と状態への参照・適用する分岐 |
| 何を受け取り返すか | API/イベント/CLI契約 | 項目・制約・認可・成功/失敗の観測可能な結果 |
| どう整合性を守るか | 所有tier、共通部分は共有仕様 | 更新対象・原子性の境界・競合判定・再送と障害回復・副作用 |
| 何を表示し何が操作できるか | presentation tier | 入出力の接続、状態の所有者、取得/送信/失敗/再送/完了の遷移 |
| 何をもって正しいとするか | 受入条件 | 具体的な入力・操作・結果。重要な境界値と失敗時に変わらない状態 |

一つの事実は一か所で編集する。他の箇所はそのIDと適用条件を参照する。
参照先は対象UCの読込範囲から解決できるファイル・見出し/operation/schemaで指定する。
型表とsummaryを別々に手直ししたり、参照先の欠落を本文の複写で埋めたりしない。
「適切に」「必要に応じて」「冪等にする」だけで挙動を決めたことにしない。

実装者に委ねてよいのは、契約とNFRを変えない内部の関数分割・局所変数名・等価なアルゴリズムなど。
業務ルールはRDRA正本で確定して参照する。技術的な認可・エラー・永続化と副作用・競合・再送結果はspecで定義する。
入力根拠にない業務仕様・UI部品契約は上流へ還流する。技術的な設計判断は根拠・影響を記録する。
入力と矛盾する判断は上流への変更要求として残し、解決前に「実装可能」としない。

## 生成時の確認

UCとその共有参照だけから、正常処理を入口→判断→更新/副作用→出力の順に辿る。
次に、実際に存在する境界で失敗させ、競合・再実行を辿る。対象のない観点の空欄は生成しない。

- 入力の取得元、必要なAPI依存、その結果を使う箇所が接続されているか。
  直リンク時にIDの取得元がないのに「再取得する」で済ませていないか。
- 状態・命令・結果に所有者が一つあるか。所有表、Props、フック、送信ハンドラの説明が一致するか。
- DBコミット、外部送信、結果保存、ACK/応答の間で停止した場合に、再送で何が起きるか。
  「同一トランザクション」とする全資源がその境界へ参加できるか。
- 冪等キーの生成・保持・更新・失効、同時到着、同じキーで異なる入力、結果不明時の扱いが決まっているか。
  成功後の別操作と、通信切断後の同じ操作の再送を区別できるか。
- 楽観ロックなら比較対象と更新条件が一致するか。条件付き更新なら必要な状態条件と更新件数0の扱いがあるか。
- 成功で変わる情報と、画面の再取得/キャッシュ無効化が対応するか。ルートIDをquery keyと混同しない。
- 日付計算の基準時刻・タイムゾーン、境界値、任意項目の欠落/null、イベント配送と再試行上限など、
  結果を左右する条件が当該UCの契約か共有仕様で決まっているか。
- BDDの値が契約の型・制約を満たすか。正常系が入力検証で落ちる例になっていないか。
  UCの業務結果とtier固有保証が同じ説明の繰り返しになっていないか。

判断が二通り以上に分かれ、結果が異なる箇所を不足/矛盾として修正する。
短さ、見出し数、図の有無、網羅表のリンク数を合格理由にしない。
反対に、削っても実装・テストの判断が一つも失われない説明は削除または正本への参照にする。

## レビューと完了判定

Step3でUC内、Step4で共有定義との接続、Step6.5で全UCの実装可能性を確認する。
実装コード全体の作成や特定モデルでの再生成は必須にしない。
難しい境界だけ、操作順序の表・疑似コード・小さな実行テストで確かめてよい。
これらはレビューの根拠であり、tier本文へ定型の疑似実装を大量追加しない。

`_review/implementation-readiness.md` にUCごとに、確認した処理経路・根拠ファイル/ID・
実装時に残る判断・判定（ready / needs-spec-change）を短く記録する。
既存のround findingsへ対応付け、同じ指摘の本文を二重管理しない。
不足のないUCに観点別の長いチェックリストを添付する必要はない。

readyは、対象範囲で結果を変える未決事項と矛盾がなく、受入結果を仕様から導ける場合だけ。
確認推奨事項へ移したこと、majorをdeferredにしたこと、レビュー上限回数に達したことは解決ではない。
結果を変えない実装裁量と軽微な表現の改善だけを残して完了できる。

## 提案を含む本文の判定

具体的な変更提案の採用後を記述した本文と、現在のlatestに対する実装着手可否を区別する。
本文の完成度だけでreadyにせず、_review/proposal-baseline.mdの全提案と最新正本を照合する。
提案どおり採用された場合は本文を維持して整合確認を記録する。異なる意味で採用された場合は影響箇所だけを修正する。
未採用の要求と生成状態は本文外のレビュー記録へ置く。本文へblockedやスキル運用の説明を差し込まない。
