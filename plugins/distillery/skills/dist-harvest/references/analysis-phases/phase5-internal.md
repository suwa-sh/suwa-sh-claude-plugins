# Phase5: システムレイヤー（情報 / 状態 / 条件 / バリエーション）

RDRA レイヤー4「システム」= システム内部の情報とルールを逆生成する。データストア定義が最強の証拠源。

- **担当レイヤー**: システム（情報・状態モデル・条件・バリエーション）
- **前提**: `analysis/01-overview.md`〜`analysis/04-boundary.md`
- **出力**: `docs/harvest/events/{event_id}/analysis/05-internal.md`
- **主な証拠源**: マイグレーション/スキーマ定義、ORM エンティティ、状態遷移コード（ステートマシン、
  `status`/`state` カラムと enum）、区分マスタ・列挙定義、バリデーション、ビジネスルールのコード

## RDRA の階層規則（再掲）

- 「情報」はビジネス上管理される ID 単位で存在する。「情報」は「情報」とつながって構造化する。
- 「状態モデル」は複数の「状態」を持ち、「UC」が状態を遷移させる。
- 「コンテキスト」は情報・状態モデル・条件・バリエーションを配下にまとめる（DDD の境界づけられた
  コンテキストに相当）。コンテキスト内の構成要素は同一 ID で管理される。
- 「条件」は「バリエーション」と「状態モデル」の組合せで出来ている（ビジネスルール）。

## 逆生成タスク

### 1. 情報（Information）

- テーブル/エンティティの主キー単位で情報を抽出する。主要属性（全部ではない）と関連情報（FK）を記録する。
- 情報を**コンテキスト**にグルーピングする。テーブルのモジュール分割・スキーマ・サブドメイン境界が手がかり。

### 2. 状態モデル（State Model）

- `status`/`state` カラムの enum、ステートマシン定義、状態遷移メソッドから状態と遷移を抽出する。
- 各状態を遷移させる UC（Phase4）と遷移先状態を関連づける。初期状態は遷移元を空欄、終了状態は
  遷移先を空欄で表す。
- 状態モデルはどの情報に属するかを記録する。

### 3. バリエーション（Variation）

- 区分・種別の列挙（会員種別、本種別、遅延日数の区分等）を抽出する。enum・区分マスタ・
  定数定義が手がかり。値をカンマ区切りで列挙する。

### 4. 条件（Condition）

- ビジネスルールを抽出する。バリデーション・ガード節・料金/上限/期限の計算ロジックが手がかり。
- 各条件が軸とするバリエーション・状態モデルを関連づける（例: 「貸出制限」は会員種別 × 蔵書の状態）。

## 整合性チェック（全 Phase 完了後に実施）

参照名と定義の整合を確認し、矛盾は `FIXME: {内容}` として該当ドキュメントに記録する:

- BUC で参照したアクター/外部システム/情報/条件が、各定義に存在するか
- 情報が参照する状態モデル/バリエーションが定義されているか、関連情報が情報として定義されているか
- 状態の遷移UC が UC 一覧に存在するか
- 条件が参照する状態モデル/バリエーションが定義されているか
- 定義したが未参照の要素がないか（あれば要否を Phase3 確認対象に）

全項目に確度と根拠を付ける（`evidence-rules.md`）。
