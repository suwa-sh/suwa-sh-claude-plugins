# Phase1: システム概要・技術スタック・ビジネスドメイン

RDRA レイヤーに入る前段として、対象システムの全体像を把握する。以降の全 Phase の土台になる。

- **担当レイヤー**: （前段・横断）
- **出力**: `docs/harvest/events/{event_id}/analysis/01-overview.md`
- **主な証拠源**: README・`docs/`・ADR、依存定義（`package.json`, `go.mod`, `pom.xml`, `Gemfile` 等）、
  ディレクトリ構成、CI 設定、`docker-compose.yml` / IaC、コミット履歴の初期

## 逆生成タスク

### 1. システム概要

- システムが提供する価値・目的を 2〜4 文で記述する（README・トップレベルドキュメントから）。
- 読めない場合はディレクトリ構成・主要エンティティから推測し `confidence: low` を付ける。
- **システム名**を 1 つ決定する。README のタイトル・リポジトリ名・パッケージ名を優先。
  この名称は後段の USDM `system_name` と RDRA `システム概要.json` の `system_name` に一致させる。

### 2. 技術スタック

- 言語・フレームワーク・データストア・主要ライブラリを依存定義から抽出する。
- フロント/バック/インフラの層構成、デプロイ形態（コンテナ/サーバレス等）を記録する。
- これらは RDRA モデルには直接載らないが、外部システム・非機能要求・情報粒度の判断材料になる。

### 3. ビジネスドメイン

- 対象の業務ドメイン（例: 図書館、EC、勤怠）を特定する。
- 主要ステークホルダー（直接・間接）を列挙する。ロール定義・認証境界が手がかり。
- ドメインの特殊性（公共性、規制、リアルタイム性等）があれば記録する。後段 NFR の入力になる。

## 出力フォーマット

```markdown
# 01 システム概要

## システム概要
- システム名: {名称}
- 目的: {2〜4文}（確度: high|medium|low / 根拠: path or 手がかり）

## 技術スタック
| 層 | 技術 | 根拠 |
|----|------|------|
| フロントエンド | {例: React 18 + TypeScript} | 事実: package.json:10 |
| バックエンド | {例: Ruby on Rails 7} | 事実: Gemfile:3 |
| データストア | {例: PostgreSQL} | 事実: config/database.yml:5 |
| デプロイ | {例: Docker + k8s} | 事実: Dockerfile, k8s/ |

## ビジネスドメイン
- ドメイン: {業務領域}
- ステークホルダー: {直接・間接の一覧}
- ドメイン特性: {公共性・規制・リアルタイム性など}（確度・根拠を添える）
```

- 全項目に `evidence-rules.md` に従い確度と根拠を付ける。
- 読み取れなかった項目は空欄にせず「推測」または「FIXME」として明示する。
