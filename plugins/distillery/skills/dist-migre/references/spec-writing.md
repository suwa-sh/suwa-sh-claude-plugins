# 仕様本文の変更点

## SPEC-CONCISE — 1.9.5

| 観点 | ガイド |
|---|---|
| 判断 | UCとtierに同じ型・手順・共通ルールがあるか。相違がある場合は単なる重複として扱わない |
| 修正 | UCは目的・データフロー・分岐つきシーケンス・受入条件、tierは接続・実行条件・技術的な振る舞いを中心に整理する。共通の技術条件は`_cross-cutting/technical-rules.md`へ集約する |
| 確認 | 旧記載の入力制約・権限・失敗時の結果・更新範囲・受入条件を一覧にし、移行後の本文または参照先で追跡できるか比較する |

文量削減を完了条件にしない。対象版で型の正本を確立できない箇所は、実装情報として必要な旧記載を維持する。

## LATEST-OWNERS — 1.11.0

| 情報 | 移行先の正本 | LLMが確認する点 |
|---|---|---|
| 業務条件・バリエーション | `rdra/latest/` | 条件ID・値・境界条件が旧specと一致するか |
| 業務状態遷移 | `rdra/latest/状態.tsv` | 遷移元・遷移先・遷移UC・条件を辿れるか |
| UIのProps・tokens・単体の振る舞い | `design/latest/storybook-app/` | 実際のexport・Story・variant・型が存在し、対象画面で使えるか |
| 共通技術条件 | `specs/latest/_cross-cutting/technical-rules.md` | 適用対象・例外・失敗時の結果が保持されるか |

本文の意味の参照はlatestにする。過去イベントへのリンクを文字列置換する前に、新旧の対象要素を照合する。
ファイルだけ存在していても、条件やStoryが失われていれば不足として記録する。
過去の判断や実行証拠を示す監査リンクは、意味の正本リンクと区別して保持する。

正本が不足している場合、旧specの具体的な振る舞いから追加案を作り、所有工程への還流要求とする。
移行しただけで上流が採用済みになったとは記録しない。
最新出力へ移行する場合の詳細は、[dist-specのlatest参照規約](../../dist-spec/references/specs/latest-linked-spec.md)を読む。

## PRODUCT-SPEC — 1.13.0

| 旧記載 | 移行後 |
|---|---|
| UC概要にスキル手順・生成状況がある | アクター・契機・達成する結果・対象範囲を書く |
| 本文に還流要求ID・採用待ち・生成状態がある | 採用後の具体的な振る舞いを本文に残し、対応と採用状態を`_review/proposal-baseline.md`へ移す |
| 「ここには書かない」等の編集指示がある | 該当定義へのリンクと適用する条件を書く |
| 冗長なtier説明がある | 処理順は図・リスト、条件や対応関係は表で記述する |

採用後の姿は、旧仕様と具体的な提案から根拠を示せるものに限る。空欄を推測で埋めない。
還流後に正本と具体案が一致したら、本文を作り直すのではなく照合結果を更新する。
不一致なら差分に影響する本文・契約を再検討する。未採用の提案を実装可能な確定仕様と誤認させないよう移行記録から状態を辿れるようにする。
最新出力へ移行する場合は、[本文の書き方](../../dist-spec/references/specs/product-spec-writing.md)と[実装可能性の基準](../../dist-spec/references/specs/implementation-readiness.md)を読む。
