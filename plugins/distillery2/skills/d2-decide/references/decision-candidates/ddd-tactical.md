# 決定候補カタログ: DDD の戦術設計

業務のルールをどの形でコードに置くかを決める。ADR の `scope: [app]`。レイヤ構成 (app-layers.md) の domain 層の中身の決めごと。
戦略設計 (コンテキストの境界) は required-decisions.md の 9 (`contexts[]`)。

---

## 適用の度合い

- **選択肢**: フル (集約・値オブジェクト・ドメインイベント・リポジトリ) / 軽量 (値オブジェクトと集約だけ) / 使わない (トランザクションスクリプト)
- **向く条件 (フル)**: 状態遷移が 5 種以上、または業務ルール (条件) が 10 件以上。不変条件 (二重予約を許さない・合計が上限を超えない) がある
- **向く条件 (軽量)**: 状態遷移はあるが少ない。不変条件が 1〜2 個
- **向く条件 (使わない)**: CRUD 中心で業務ルールがほぼ無い

## 決めること

- **集約の境界**: 1 つのトランザクションで守る不変条件の範囲。RDRA の情報と状態モデルから、同時に更新される情報の塊を集約にする (他の集約は id で参照する)
- **値オブジェクト**: 期間・金額・識別子のように、値で比べて検証を持つもの。生のプリミティブを業務の値に使わない
- **ドメインイベント**: 状態が変わった事実 (予約が確定した など) を名前付きで出すか。出すなら、後続の処理 (通知・集計) はイベントを購読する
- **リポジトリ**: 集約ごとに 1 つ。集約の外の部分を直接保存しない

## 派生するルール例

```yaml
- scope: tier:backend
  text: "業務の不変条件は集約のメソッドで守る。usecase やハンドラに条件分岐で書かない"
- scope: tier:backend
  text: "期間・金額・識別子は値オブジェクトにし、生成のときに検証する (不正な値のインスタンスを作れない)"
- scope: tier:backend
  text: "集約の外の集約は id で参照し、1 つのトランザクションで 2 つの集約を更新しない"
```
