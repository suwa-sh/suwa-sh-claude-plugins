# 決定候補カタログ: エラーハンドリング

エラーの種類・表し方・層ごとの扱い・利用者への返し方を決める。ADR の `scope: [app]`。契約のエラー型 (d2-contract の骨格の `Problem`) と揃える。

---

## エラーの種類

- **業務のエラー**: 業務ルールに反した (予約が重なる・期限を過ぎた)。利用者に理由を返す。再試行しても同じ
- **入力のエラー**: 形が不正 (必須が無い・形式が違う)。契約の検証で返す
- **見つからない・権限が無い**: 対象が無い / 見る・変える権限が無い (認可の決定と揃える)
- **システムのエラー**: DB や外部サービスの失敗・想定外。利用者には詳細を出さず、ログに残す。再試行できるものは再試行する

## 決めること

- **表し方**: 例外 / 戻り値 (Result 型)。domain と usecase は業務のエラーを型で表す (呼ぶ側が扱いを忘れない) か、例外で投げるか
- **層ごとの扱い**: domain は業務のエラーを作るだけ / usecase は業務のエラーをそのまま返し、システムのエラーを包む / presentation が契約のエラー型と HTTP の status に変える
- **返し方**: 契約のエラー型 (`Problem` の `type`・`title`・`detail`・業務のエラーのコード) と status の対応表
- **再試行と冪等**: ここでは決めない。冪等性と再試行の ADR (idempotency-retry.md) で、送り直しの扱い・再試行する範囲・時間切れをまとめて決める

## 派生するルール例

```yaml
- scope: tier:backend
  text: "業務のエラーは domain でコード付きの型として作り、presentation で契約のエラー型と status に変える (業務のエラーで 500 を返さない)"
- scope: tier:backend
  text: "システムのエラーの詳細 (スタック・SQL) を応答に出さない。ログに残し、応答は汎用の文と相関 ID だけ"
- scope: tier:frontend
  text: "業務のエラーは契約のエラー型のコードで分岐し、利用者に理由を表示する"
```
