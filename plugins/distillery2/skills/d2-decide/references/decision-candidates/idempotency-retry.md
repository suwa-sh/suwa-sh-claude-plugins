# 決定候補カタログ: 冪等性と再試行

同じ要求がもう一度届いたときの扱いと、失敗したときにやり直す範囲を決める。ADR の `scope: [app]`。
エラーハンドリング (error-handling.md) とメッセージング (messaging.md) にまたがるので、1 本の ADR にまとめて決める。更新する UC が 1 つでもあれば必ず決める (読むだけのプロダクトは「不要」と明記する)。

---

## なぜ 1 つの領域にするか

- 応答が届かないと、利用者や画面は同じ要求を送り直す。送り直しの扱いを決めないまま実装すると、二重登録か、成立済みなのにエラー、のどちらかになる
- 「冪等キーを入れるか」だけを決めると抜ける。キーを入れないなら、送り直しを何で見分けて何を返すかを決める
- 画面・API・DB・非同期の処理で対処がそろっていないと、どこか 1 か所で重複する

## 決めること

- **同じ要求の見分け方**: 冪等キー (要求ごとの一意な値を利用側が付ける) / 業務の内容 (同じ人・同じ対象・同じ値) / 見分けない
- **見分けたときの返し方**: 前回と同じ成功の応答を返す / 重複のエラーを返す。成功を返すなら、状態が変わった後 (期限を過ぎたなど) でも返すか
- **判定の順番**: 送り直しの判定を、ほかの検査 (過去の日時・権限・重なり) より先に行うか後に行うか
- **最後の砦**: アプリの事前の確認だけに頼らず、DB の一意制約などで重複を止めるか
- **再試行する範囲**: 再試行するのはシステムのエラーだけ (業務のエラーは再試行しても同じ)。誰が (画面・API の利用側・非同期の処理)、何回まで、どの間隔で
- **時間切れ**: 外部の呼び出しと DB に時間切れを置くか。時間切れの後に結果が分からない要求を、送り直しとして扱えるか
- **非同期の処理**: メッセージやジョブを 2 回受けても結果が変わらない作りにするか (メッセージングを使うときだけ)

## 向く条件

- **冪等キー (high)**: 金銭の取引・外部の決済・社外の利用者からの更新。業務の内容では同じ要求かどうかを決められない (同じ内容の注文を 2 回してよい) とき
- **業務の内容で見分ける (medium)**: 同じ人が同じ対象に同じ値で 2 回登録することが業務として起きない (同じ会議室・同じ時間帯の予約など) とき。キーを保存する仕組みが要らない
- **見分けない (low)**: 重複しても害が無い (上書きの更新・既読の印など) とき

## 層ごとの対処の例

| 層 | 対処 |
|---|---|
| frontend | 送信中はボタンを押せなくする。冪等キーを使うなら要求ごとに作って付ける |
| backend-api | 冪等キーか業務の内容で送り直しを見分け、決めた応答を返す。判定の順番を usecase に置く |
| RDB | 一意制約で重複を止め、違反を業務のエラーか「成立済み」に変える |
| worker / メッセージ | メッセージの ID やジョブの実行 ID で 2 回目を捨てる |

## 派生するルール例

```yaml
- scope: common
  text: "同じ内容の送り直し (同じ人・同じ対象・同じ値) は新しく登録せず、成立済みの結果を成功として返す"
- scope: tier:backend
  text: "送り直しの判定は usecase で、ほかの業務の検査より先に行う"
- scope: tier:backend
  text: "重複の最後の砦は DB の一意制約にする。アプリの事前の確認だけに頼らない"
- scope: tier:frontend
  text: "更新の要求を送っている間は送信のボタンを押せなくする。自動で再試行するのはシステムのエラーだけ"
- scope: tier:worker
  text: "同じメッセージ ID を 2 回受けても、副作用を重複させない"   # 非同期の処理を採るときだけ
```
