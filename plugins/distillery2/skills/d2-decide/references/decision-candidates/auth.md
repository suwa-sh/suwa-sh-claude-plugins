# 決定候補カタログ: 認証 / 認可

認証方式と認可モデルを決める。ADR の `scope: [system]` (認証基盤) / `[app]` (認可の実装位置)。

---

## 認証 (authn)

- **選択肢**: OAuth2/OIDC + IdP 委譲 (Federated Identity) / 簡易認証 (自前)
- **向く条件 (委譲)**: 外部アクターが存在、または SSO が必要。
- **IdP 方式**: 外部向け + ソーシャルログイン → マネージド IdP。社内のみ / 既存ディレクトリ → セルフホスト。混在 → 併用 (確信度 low)。
- **派生するルール例**:
  ```yaml
  - scope: common
    text: "認証は OIDC の ID トークンで行い、アプリはトークン検証だけを担いパスワードを保持しない"
  ```

## 認可 (authz) モデル

- **選択肢**:
  - A: RBAC + backend 作り込み (小規模・パターン少、認可サービス不要)
  - B: RBAC + Policy Engine (条件ベースが多い)
  - C: ReBAC 外部サービス (所有権ベースが多い)
  - D: ReBAC + ABAC ハイブリッド (所有権 + 条件が両方多く大規模)
- **認可パターン分析**: ロールベース / 所有権ベース / 条件ベース / 状態ベース。状態ベースは authz に含めず domain のビジネスルールで実装する。

### 選定の重み付け (重要)

1. **一次判定 = データ感度 / 法規制**が決定要因。決済・金銭 / 個人情報 / 認証情報 / 医療 / 監査ログ / 明示的法規制 (GDPR / PCI DSS / HIPAA) に該当 → サブドメイン種別に関係なく厳格認可 (ABAC + domain 状態ベース) を必須とする。
2. データ感度が低い場合のみ、**二次判定 = 認可パターンの複雑度**: 所有権 3 以上 → ReBAC、条件 3 以上 → Policy Engine、ロールのみ少数 → RBAC。
3. サブドメイン種別 (Core/Supporting/Generic) は補助シグナルのみ。「Generic だから簡易」は危険 (決済 / 請求 / 監査ログは汎用でも高感度)。戦略分類とセキュリティ感度を混同しない。

- **派生するルール例**:
  ```yaml
  - scope: common
    text: "リソース参照は所有者・ロール・状態を認可チェックしてから返し、認可判定を presentation に散らさない"
  ```

## 参考: 関連クラウドパターン
