# 戦略 → 戦術の落とし込みと配置形態

戦略的設計(問題空間)と戦術的設計(解決空間)をつなぐのは **境界づけられたコンテキスト(BC)**。設計は「戦略(境界)を先に決め、その内側でのみ戦術を語る」。

## 落とし込みの連鎖(粒度を下げる)

```
コンテキスト境界(言語の一貫範囲)
   ↓ その中で
集約境界(必ず守りたい強整合の最小単位)
   ↓ その中で
値オブジェクト / エンティティ(言語の概念を不変・等価で型化)
```

- 境界を跨いだ集約・値オブジェクトの共有はしない。
- 集約境界 = トランザクション整合性の境界。コンテキスト境界の内側で、強整合が必須の最小単位を集約にする。
- 値オブジェクトはユビキタス言語の概念(金額・期間・識別子)を型にする = 言語をコードに翻訳する最小粒度。
- 集約内部の実装(コード)は **ddd-tactical-implementation スキル**に引き継ぐ。

## 配置形態(モジュラモノリス / マイクロサービス)

- BC は配置中立: **モジュラモノリスでは BC = モジュール**(例 `Clinical/` `Billing/`)、**マイクロサービスでは BC = 独立サービス**。
- **まずモジュラモノリスで BC 境界を固め、整合が取れてから必要箇所だけサービス分割**する(early microservices は分散モノリス化リスク)。よく整理されたモジュラモノリスは後の分割準備が整っている。
- 境界を間違えると "分散モノリス" になる。

## 境界の強制ルール(分割可否のチェックリスト)

- [ ] コンテキスト跨ぎの直接DBアクセスを禁止しているか。
- [ ] 共有ドメインエンティティを持っていないか(共有するのは ID と統合イベントのみ)。
- [ ] 境界で翻訳しているか(ACL or Published Language)。
- [ ] DB を分けたか / エンティティを共有していないか。

## 注意

- Evans は「1マイクロサービス = 1BC」と短絡しないよう警告。サービスには Service Internal / API of Service / 協調クラスタ / Interchange Context の4つのコンテキストが絡む。機械的に 1:1 でサービス化しない。
- マイクロサービス化はスケーラビリティ重視のときの特殊解と捉え、トレードオフを評価する。
