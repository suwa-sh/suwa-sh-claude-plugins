# 境界づけられたコンテキスト(Bounded Context)の引き方

特定の用語・定義・ルールが一貫して適用されるソフトウェアの境界。各コンテキストは自前のドメインモデル・ユビキタス言語・(理想的には)DBスキーマを持つ。DDD 戦略的設計の中心パターン。

## 境界を引く力

1. **言語の境界(第一の力)**: モデルはユビキタス言語として機能するので、**言語が変わる(同じ単語が別の意味になる)地点**にコンテキスト境界がある。
   - 例: 電力会社の "meter" が部門により grid 接続 / 顧客関係 / 物理デバイスと意味が変わる。"Customer" が販売文脈と請求文脈で別物。
2. **チームの境界(Conway の法則)**: 設計はチームのコミュニケーション構造を写す。コンテキストをチーム境界に揃えると 1チーム=1つの一貫したモデル/言語を所有できる。1モデルを複数チームで共有すると言語が割れて破綻しやすい。

## サイジングの勘所

- **大きすぎる** = 言語が割れて統一モデルが崩れる。
- **小さすぎる** = 統合コストが膨らむ。
- 狙いは**言語の一貫性が保てる最大単位**。

## ユビキタス言語

- 開発者と利用者の間で共通かつ厳密な言語を構築し、**会話とコードの両方で徹底**使用する(クラス名・メソッド名・テーブル名にドメイン用語をそのまま)。
- **コンテキストごとに1つ**。語彙が割れる場所が境界の発見ポイント。
- ドメインエキスパートが使わない技術語をモデルに混ぜない。Slack の会話やコミットコメントにも同じ語彙が出てくるはず。ズレたらモデルを直す。

## 実務の進め方

- ドメインエキスパートとの会話で用語・ルールが一貫する範囲を1コンテキストにまとめる。
- 境界発見にはモデリングだけでなく Domain Storytelling 等の協働ワークショップ技法を併用してもよい。
- 全社で1つの巨大モデルを目指さない。完全統一は実現可能でもコスト見合いでもない(Evans)。
