# DDD 戦略的設計 アーキテクチャガイド

大きな問題を「どう分割し、コンテキスト間の関係をどう結ぶか」を決める。これは**問題空間**(言語・制約・境界)の設計であり、技術選択(解決空間)より先に行う。設計判断の「問い」を順に通すチェックリスト型のスキル。

戦略的設計は **境界づけられたコンテキスト(Bounded Context)** を蝶番に、サブドメイン分類で投資配分を決め、コンテキストマップで統合方式を選び、最後に戦術設計(集約・値オブジェクト)へ落とし込む。

## 設計の問い(この順で通す)

### Q1. サブドメインを分類したか? → `references/subdomain.md`
- Core(競争優位の源泉)/ Supporting(コアを支えるが差別化でない)/ Generic(どこにでもある)を仕分ける。
- 投資配分: Core に最大の DDD 投資、Supporting は good enough、Generic は買う/借りる(自作しない)。
- 判断の問い: 「ここで他社に勝つか?」Yes → Core。

### Q2. 境界づけられたコンテキストを引いたか? → `references/bounded-context.md`
- 第一の力は**言語の境界**(同じ単語の意味が割れる地点。例: "Customer" が販売文脈と請求文脈で別物)。
- **チーム境界(Conway の法則)** と揃える(1チーム=1つの一貫モデル/言語)。
- 全社1巨大モデルを目指さない。言語の一貫性が保てる最大単位を狙う(大きすぎ=言語が割れる/小さすぎ=統合コスト膨張)。
- ユビキタス言語はコンテキストごとに1つ。

### Q3. コンテキスト間の関係(統合方式)を選んだか? → `references/context-map.md`
- 上流/下流の力関係で選ぶ: Shared Kernel / Customer-Supplier / Conformist / Anti-Corruption Layer(ACL)/ Open Host Service(OHS)/ Published Language。
- 影響力ゼロ → Conformist か ACL。汚いモデルを取り込みたくない → ACL を挟む。下流多数 → OHS + Published Language。

### Q4. 戦術への落とし込み・配置形態を決めたか? → `references/strategy-to-tactics.md`
- 連鎖: **コンテキスト境界(言語の一貫範囲)→ 集約境界(強整合の最小単位)→ 値オブジェクト(言語の概念を型化)**。
- 配置: モジュラモノリスでは BC=モジュール、マイクロサービスでは BC=独立サービス。まずモジュラモノリスで境界を固め、整合後に必要箇所だけサービス分割(early microservices は分散モノリス化リスク)。
- 境界の強制ルール: コンテキスト跨ぎの直接DBアクセス禁止 / 共有ドメインエンティティ禁止(共有は ID と統合イベントのみ)/ 境界で翻訳(ACL or Published Language)。

## 成果物イメージ

- サブドメイン分類表(Core/Supporting/Generic + 投資方針)
- 境界づけられたコンテキストの一覧と、各コンテキストのユビキタス言語の核語彙
- コンテキストマップ(関係パターン + 依存方向 + 翻訳責務)
- 集約境界の初期仮説(→ 実装は ddd-tactical-implementation スキルへ引き継ぐ)

## 注意

- **戦略 ≥ 戦術の順序**を守る。境界を先に決め、その内側でのみ戦術を語る。境界を跨いだ集約・値オブジェクト共有はしない。
- 戦略的設計は完璧な整然さを目指さない(Evans「理想的に整然としたシステムは稀」)。Bounded Context と Subdomain は現実には misaligned しうる前提で進める。
- DDD は唯一解ではない。単純なドメインに戦略的設計を重く適用しない(「Not every good design needs to be Domain-driven」)。
