# 集約(Aggregate)設計とモデリング

little_hands(松岡幸一郎)流の実務判断を中核に、集約境界の引き方とモデリングの進め方を示す。

## 集約とは

- **必ず守りたい強い整合性を持つオブジェクトのまとまり** = 整合性の境界 = **リポジトリから出し入れする単位**(取得・更新の単位)。
- 集約の範囲が決まると、エンティティ・値オブジェクト・リポジトリの実装形が決まる(リポジトリは集約に対して1つ)。

## 核ルール

- **強整合(同一トランザクションで必ず守りたい不変条件)があるものだけ同一集約**にまとめる。なければ分ける。
- **1トランザクション1集約**(必ず1つのトランザクションでまとめて更新)。
- リポジトリは**集約単位で取得・保存**(部分取得・部分更新をしない)。
- 集約をまたぐ参照は**集約ルートの ID 参照のみ**(別集約のインスタンスを直接フィールド保持しない)。理由: インスタンス参照を許すと別集約のものもリポジトリから取れてしまい、依存が上がる。

## 集約設計チェックリスト

- [ ] 強整合があるものだけ同一集約にしているか。
- [ ] 1トランザクションで更新するのは1集約か。複数集約をまたぐ更新なら境界/トランザクション設計を疑う。
- [ ] 集約をまたぐ参照は ID 参照か(別集約のエンティティを直接保持していないか)。
- [ ] 子を他集約から参照したくなったら → その子を独立した別集約に切り出す。
- [ ] 件数が多い子コレクションは、親が直接保持せず別集約 + ID 参照にする(親集約の肥大を防ぐ)。
- [ ] アプリで使わない DB カラムはオブジェクトに載せない(リポジトリの詰め替えで吸収)。1テーブルでもマッピング先を複数集約に分けてよい。

> 集約の範囲は確定的に決め切らず**仮説検証型**で進める。「良し悪しは実装してみないとわかることが多い」。問題が出たらドメインモデル図に戻って更新する。集約を小さく保つことの根拠(大集約の性能害)は `applicability-and-pitfalls.md`。

## 集約をまたぐ整合性確保(3方式・コスト×確実性で選択、混在可)

1. **ユースケースで複数集約を更新** — 最シンプル。ただし他のユースケースで集約間の関係を破壊することは防げない。
2. **ドメインサービスを使用** — 整合ロジックをドメイン層に移せる。可視性制御で不正生成をコンパイル時に防げるが、責務が曖昧になりがち。
3. **ドメインイベントを使用** — 確実に整合を確保できるが、実装複雑度・導入ハードルが高い。

> どれが正解ということはなく、実装コストと整合性の重要性のバランスで選ぶ。「まとめて確実に整合を取りたい」操作(口座間送金など)は1ユースケースにまとめ、なんならドメイン層で保証する。

## エンティティと値オブジェクトの使い分け

- 分岐軸は **identity(一意識別子・ライフサイクルを通じた同一性)の有無**。要る=エンティティ、不要(値で同一性判断)=値オブジェクト。
- VO/Entity の確定は**モデル図段階でなく集約設計・実装のタイミング**でよい。図段階は制約の洗い出しを優先。

## モデリングの進め方(sudoモデリング = S・U・D・O の4図)

実装に落とすための最小ラインナップ。

- **S = システム関連図** — 開発システムとアクター・外部システムの関連。スコープ把握。
- **U = ユースケース図** — ユーザー要求に対するシステムの振る舞い。スコープ限定。
- **D = ドメインモデル図** — 簡易クラス図。オブジェクト間関係と制約を表現。
- **O = オブジェクト図** — ドメインモデルの**具体例**。

進め方: 抽象化が難しければ**先に具体例(オブジェクト図)を量産** → 抽象化 → 集約設計 → コード。最終段階で集約の範囲を決定(仮説検証型)。

**ドメインモデル図の書き方**: メソッドは書かなくてよい。**「ルール/制約(ドメイン知識)」を吹き出しに書き出す**のが本体。オブジェクト間の関連・多重度・集約の範囲・日英対訳を定義する。

## 層責務(ドメイン層とユースケース層の分離)

- ユースケースは**ファサード、1処理1つ**。ユースケース同士を呼ばない(共通処理は別オブジェクトに切り出す)。
- **ドメインオブジェクトはリポジトリ/インフラに依存しない**。集約外の取得はユースケースで行い、結果を引数でドメインメソッドに渡す。
- **setter 非公開**(外から不整合状態を作れない)。業務ルールはドメインオブジェクトのメソッドへ。
- データモデル(永続化都合)とドメインモデルを混同しない。リポジトリ実装で詰め替える。ドメインモデルを先に設計する。
