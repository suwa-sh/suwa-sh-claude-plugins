# オブジェクト指向プラクティス(戦術設計の土台)

戦術要素(値オブジェクト/エンティティ/集約)は、OO の凝集・結合・単一責任(SRP)を DDD 語彙で具体化したもの。データと振る舞いの同居が貫通原則。

## ドメインモデル貧血症の回避

- **貧血モデル = データだけ持ち振る舞いを持たない getter/setter の袋**。Fowler がアンチパターンと断じた(「OO の基本理念=データとプロセスの結合に真っ向から反する」「手続き型」)。
- データと振る舞いを分離すると凝集が壊れ、高結合・重複を生む。
- **危険信号**: ドメインクラスが getter/setter のみ / ルールが Service に偏在 / 同じ計算が複数箇所に重複。
- **対処**: そのデータを使う判断・計算をドメインオブジェクトに同居させる。Service 層は調整役(thin)に保ち、業務ルールはエンティティ/値オブジェクトに置く。
- 例外(貧血が正しい場面)は `applicability-and-pitfalls.md`(ステートレス/FP/CQRS read)。

## Tell, Don't Ask

- データを取り出して呼び出し側で if 判定するより、**振る舞いをオブジェクトのメソッドにして「命じる」**。これは貧血回避と整合する。
- **ただし教条化しない**(Fowler 自身の留保): getter 全廃(GetterEradicator)を戒める。純粋な情報提供 query は残してよい。良い設計はトレードオフで、データと振る舞いの近接はその一要素。

## デメテルの法則(最小知識)

- `a.getB().getC().doX()`(列車事故チェーン)を避け、中間を委譲メソッドで隠して結合を下げる。

## 不変条件のカプセル化(Always-Valid)

- エンティティ/集約は**常に有効**であるべき。コンストラクタ/ファクトリで全不変条件を検証し、満たさなければ例外で生成を拒否する(半端な状態を作れない)。
- setter を排し、状態遷移は不変条件を保証するメソッド経由のみにする。
- 整合性責務は集約ルートに閉じる(SRP =「自分の整合性は自分で守る」)。
- **重要な分離**(`applicability-and-pitfalls.md` 論点2): Always-Valid は**不変条件(invariant)に限定**。入力検証(input validation)はアプリケーション層で行い、集約内に混ぜない。
- **実行時境界の再検証(外しやすい・最重要)**: **型注釈・コンパイル時の型は実行時を守らない**。生成時に検証しても、次の境界では関所(コンストラクタ/ファクトリ)を**迂回**して不正状態が入り込む:
  - **永続化からの復元(reconstitution)**: DB/JSON 復元の経路が無検証だと、`request()` 等で弾く不正状態を作れてしまう。「新規生成」と「復元」を別ファクトリに分け、**両方で実行時検証**する。
  - **API/外部入力・共有DB由来データ**: 外部由来の値(状態文字列・日付・数値)を型注釈だけで信用しない。「潜在的に不正」と仮定して再検証する。
  - 言語別の具体(TS の `as` キャストは実行時無検証 / Python の型ヒントは無効 / Go の日付正規化など)は `language-notes.md`。

## null / 例外(Fail-Fast / Null Object)

- 「あとで壊れる」より「今すぐ生成で失敗」を選ぶ。不正値はコンストラクタで例外。
- 「無し」を生 null でばら撒かず、Null Object か Optional / 型で表現し、呼び出し側の null チェックを上流で消す。
- null を返さない / null を引数で受けない文化を前提にする(増田流)。

## 凝集・結合・SRP との対応

- 「このデータを使う判断はどこにあるべきか」→ **凝集**で決める(データの隣に振る舞い)。
- 「この変更で何箇所が連鎖して壊れるか」→ **結合**で測る(チェーン依存・getter 経由判断を削る)。
- 「整合性を守る責務は誰か」→ **SRP**で決める(集約ルートに閉じ込め、外から不変条件を破れなくする)。
- まとめ: 値オブジェクト=概念ごとの高凝集な不変型 / エンティティ=識別子で同一性を持つ振る舞いの所在 / 集約=強整合の境界=トランザクション整合の単一責務単位。

## イミュータブルなデータ設計(増田流・任意)

- 事実は上書きせず追記し(INSERT only)、状態・残高・集計は事実の履歴から導出する。「NULL という事実はない」。
- 適用は**履歴/監査要件があるリソース系に限定**し、スナップショット併用を前提にする(運用コストは `applicability-and-pitfalls.md` 論点8)。削除フラグ等の物理パターンを一律禁止しない。
