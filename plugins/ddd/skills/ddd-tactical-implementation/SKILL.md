# DDD 戦術設計 実装ガイド

ドメインモデルを「業務の関心事(ルール・制約)が読めるコード」に落とすための戦術設計を適用する。例は Java 主軸だが考え方は言語非依存で、TypeScript / Python / Go / Kotlin など他言語でも読み替えて使える。**Java を写経せず各言語のイディオムに翻訳**し、言語別の翻訳指針と落とし穴は `references/language-notes.md` を参照する(特に「実行時境界の再検証」)。

戦術パターン(値オブジェクト等)は**目的でなく手段**である。目的は業務ルールをコードに明示し、変更を楽で安全にすること。型だけ真似てモデリングしない状態(軽量DDD / なんちゃってDDD)を避ける。

## まず適用判断ゲート(スキップ禁止)

戦術DDDは**複雑なドメインで報われる**。単純な対象に適用すると逆効果(実測で完全DDDは素朴実装の約8〜9倍のコード量になりうる)。実装に入る前に必ず問う:

1. **このドメインは Core か / 本質的に複雑か?** — No(単純CRUD・管理画面・Genericサブドメイン・短命MVP・1〜2人/数週間)なら、**トランザクションスクリプトやアクティブレコードを許容**し、本スキルの戦術パターンを無理に適用しない。
2. **モデリング(ルール・制約の洗い出し)を済ませたか?** — No なら先に行う。具体例を並べて抽象化する進め方は `references/aggregate.md`(sudoモデリング)を参照。戦術パターンをモデリングより先に入れると「巨大な泥団子」化する。
3. Yes が揃ったら下の中核ワークフローへ。

> 戦略的設計(境界づけられたコンテキスト/サブドメイン分類/集約境界の引き方)が未確定なら、先に **ddd-architecture スキル**を使う。戦略 → 戦術の順序を守る。

## 中核ワークフロー

1. **モデルのルール/制約を確認** — どの不変条件・業務ルールをコードで守るかを言語化(ユビキタス言語をそのまま命名に使う)。
2. **集約境界を引く** — 強整合を守る最小単位。1トランザクション1集約、他集約は ID 参照。判断基準とチェックリストは `references/aggregate.md`。
3. **値を型で表現** — 基本型(int/String/Date)を裸で引き回さず、振る舞い/不変条件を持つ値をドメイン固有型に包む。型カタログ・計算候補表・命名規約は `references/value-objects.md`。
4. **区分は振る舞いを持った enum へ** — if/switch をオブジェクトに置換。2フォーム(constant-specific method / Strategy 委譲)の使い分けと確定サンプルは `references/behavior-rich-enum.md`。
5. **コレクションはファーストクラスコレクションに** — 生 List/Set/Map を引き回さず専用クラスでラップ。メソッド候補は `references/first-class-collection.md`。
6. **データと振る舞いを同居(貧血回避)** — setter 非公開、判定/計算をオブジェクト内へ。ユースケース層との責務分離・Tell Don't Ask・不変条件カプセル化は `references/oo-practices.md`。
7. **やりすぎ兆候を点検** — 各パターンの「いつ裏目に出るか / ORM・言語による妥協」は `references/applicability-and-pitfalls.md`。

## レビュー観点(チェックリスト)

- [ ] 業務ルール(吹き出しの知識)がコードのどのクラス/メソッドに実装されているか追えるか(追えなければ軽量DDD)。
- [ ] 基本型を裸で引き回していないか。振る舞いのある値が VO になっているか(逆に、振る舞いのない単なる型安全ラップを乱造していないか)。
- [ ] getter で取り出して呼び出し側で if 判定していないか → 判定メソッドへ。
- [ ] 区分の switch/if が散在していないか → enum へ凝集。
- [ ] setter が公開され外から不整合状態を作れないか。
- [ ] 集約をまたぐ参照を直接インスタンスで保持していないか(ID 参照か)。1トランザクションで複数集約を更新していないか。
- [ ] 入力検証と不変条件を同一クラスに混ぜていないか(検証はアプリ層、不変条件は集約内)。
- [ ] 生成の関所(コンストラクタ/ファクトリ)を、**永続化からの復元(reconstitution)や API 入力の経路ですり抜けさせていないか**。型注釈・コンパイル時型は実行時を守らない。境界では再検証する(言語別の具体は `references/language-notes.md`)。

各プラクティスの出典 URL は各 reference ファイルの末尾に記載。増田亨・little_hands(松岡幸一郎)・Martin Fowler・Vaughn Vernon・Vladimir Khorikov の知見をベースにしている。
