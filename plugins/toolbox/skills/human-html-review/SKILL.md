# Human HTML Review

ヒトに判断を求めるページを作る。読者は「作業の文脈を忘れている同僚」だと考える。

## 守ること (優先順)

| # | 原則 | 具体的に |
|---|---|---|
| 1 | 読者は文脈を忘れている | 冒頭で「何の作業で、いまどこで、なぜ止まって聞くのか」を思い出させる |
| 2 | 平易な言葉 | 専門用語は言い換えるか、初出で 1 行説明する |
| 3 | ID ではなく名前 | `UC-06` / `fd678b04` / `S3` のような内部 ID を本文に出さない。名前で呼ぶ |
| 4 | テクニカルライティング | 一文一義。結論を先に。同じものは同じ名前で呼ぶ |
| 5 | 文章より構造 | 3 文を超える段落は、リスト・表・見出しに分解する |
| 6 | 構造より図解 | 流れ・構成・関係・前後比較・位置づけは図で見せる |
| 7 | 横幅を使う | 本文幅の上限は 1760px。図と説明を横に並べる |

固定フォーマットは無い。**構成は毎回、読者の問いの順に組む。**

## 入力

`$ARGUMENTS` = レビュー対象 + 任意の出力パス。対象の指定が無ければ、いまの会話で判断待ちになっている事柄を対象にする。

```text
$human-html-review                      # いま止まっている確認事項
$human-html-review current changes      # 作業ツリーの変更
$human-html-review この設計案 --output tmp/reviews/auth-design.html
```

- 出力先のデフォルト: リポジトリ配下の `tmp/reviews/<対象>-review.html`
- 既存ファイルは上書きしない。`-2`, `-3` のように連番を付ける
- コミット・公開・正式な承認記録は、指示が無い限りしない

## ワークフロー

### 1. 読者の問いを書き出す (HTML を書く前)

[references/content-design.md](references/content-design.md) を読み、**読者が上から順に抱く問い**を 5〜8 個書き出す。最初の 3 つは固定:

1. これは何の話? いまどこ?
2. 何を決めてほしい?
3. 決めるために何を知ればいい?

4 つ目以降は対象ごとに変わる (例: 「他の案は?」「何が壊れうる?」「戻せる?」「決めたら何が起きる?」)。

### 2. 問いごとに「見せ方」を決める

各問いに対して、次の順で表現を選ぶ。**上にあるほど優先**。

| 見せ方 | 向いている内容 |
|---|---|
| 図 | 流れ、構成、関係、前後の違い、位置づけ、状態遷移、全体の中の現在地 |
| 表 | 比較、対応関係、一覧、数値 |
| リスト | 手順、条件、並列の事実 |
| 短い文 | 結論、理由、注意 (3 文まで) |

図の選び方は [references/diagrams.md](references/diagrams.md)。**目安: 見出し 2 つにつき図 1 つ以上。**

### 3. 事実の台帳を作る

本文に書く主張を、根拠つきで分類する。分類ラベルは本文にも出す (色だけに頼らない)。

| ラベル | 意味 |
|---|---|
| 確認済み | コード・差分・実行結果・仕様で直接確かめた |
| 報告のみ | エージェントの報告だが、独立には確かめていない |
| 推測 | 前提を置いた解釈。前提を書く |
| 未確認 | 根拠が無い。読者に確認してほしいこと |

根拠が無いことを、あるように書かない。欠けていれば「未確認」と書く。

### 4. 言葉を整える

書き終えた下書きに対して:

- 内部 ID → 名前に置換する (対応表は付録に置いてよい。本文には出さない)
- 専門用語 → 平易な語に置換するか、初出で 1 行説明する
- 3 文を超える段落 → リストか表にする
- 同じものを違う名前で呼んでいないか揃える

### 5. HTML を組む

[assets/base.html](assets/base.html) をコピーし、[references/components.md](references/components.md) の部品を組み合わせて 1 ファイルで書き切る。

必須の要素は 3 つだけ:

| 要素 | 属性 | 内容 |
|---|---|---|
| いま何の話か | `data-role="context"` | 最初の画面に入る。作業の目的、現在地、なぜ止まって聞くのか |
| 何を決めてほしいか | `data-role="ask"` | 問い 1 文 + 答え方の種類 (承認 / 選択 / 記入) |
| どう答えるか | `data-role="reply"` | コピーして返せる回答例 |

制約:

- 自己完結の 1 ファイル。外部フォント・CDN・iframe・form・JavaScript を使わない
- 図はインライン SVG。`role="img"` と `<title>` を付け、`<figure>` で包んで `<figcaption>` を添える
- 状態や分類は色だけで表さない。必ず文字ラベルを添える
- 390px 幅で本文が横スクロールしない (表と図は個別に横スクロール可)
- viewBox 幅 400 超の図は `figure.fig.scroll` + `style="--min: <viewBox 幅>px"` にして、狭い画面で縮めずに横スクロールさせる。縮めると文字が読めなくなる

### 6. 検証する

```bash
# <skill-base-dir> = スキル読込時に表示される "Base directory for this skill"
python3 "<skill-base-dir>/scripts/validate.py" "<output.html>"
```

- `ERROR` はすべて直す
- `WARN` (内部 ID らしき文字列 / 4 文以上または 160 字超の段落 / 図解不足 / 幅不足) は 1 件ずつ見て、直すか、残す理由を完了報告に書く
- 内部 ID の検査は `<pre>` / `<kbd>` / `<samp>` (コマンド・回答例) と付録 (`data-role="appendix"`) だけを除外する。inline の `<code>`、見出し、図の中の文字 (`<text>`) は本文扱い

その後、ブラウザかスクリーンショットで狭い幅と広い幅を目視する。目視できない場合は「目視していない」と報告する。

### 7. 見せる

ユーザースコープの `showme` スキルが使える環境では publish し、URL を「スマホで開く: <url>」の形で提示する。使えなければローカルパスだけを提示する。

## 完了時の報告

- 出力の絶対パス (と showme の URL)
- 読者に求めている判断を 1 文で
- validator の結果 (残した WARN と理由)
- 目視確認をしたか
- 本文に書けなかった「未確認」事項

## diagram-design との関係 (任意)

`~/.claude/skills/diagram-design/` か `.claude/skills/diagram-design/` があれば、図の描き方 (ノードの装飾、直角コネクタ、複雑さの上限) はそのスキルに従う。無ければ [references/diagrams.md](references/diagrams.md) の最小ルールだけで描く。インストールを求めない。

競合時はこのスキルが勝つ: 外部フォントを読み込まない、図は個別 HTML にせずレビュー HTML にインラインで埋める。
