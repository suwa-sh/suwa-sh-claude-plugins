# コンテンツ設計: 読者の問いの順に組む

固定の章立ては無い。**読者が上から読んで順に抱く問い**を先に書き出し、その順に答える。

## 読者像

- 作業の文脈を忘れている。昨日の会話も、ファイル名も、ID も覚えていない
- スマホで開くこともある。1 画面目で「何の話か」が分からなければ閉じる
- 判断はしたい。だが読み込む時間は 3 分しかない

この読者に「同僚が休暇明けに読む引き継ぎメモ」として書く。

## 問いの階段

最初の 3 段は固定。4 段目以降は対象に合わせて選ぶ。

```text
1. これは何の話? いまどこ?          ← data-role="context"  (最初の画面)
2. 何を決めてほしい?                ← data-role="ask"      (最初の画面)
3. 決めるために何を知ればいい?      ← 対象ごとに 2〜5 個に分解
4. (対象ごと) 他の案は? / 何が壊れうる? / 戻せる? / 根拠は?
5. 決めたら何が起きる?
6. どう答える?                      ← data-role="reply"
7. 付録: 生データ、用語と ID の対応、対象外にしたこと
```

### 1. これは何の話? いまどこ?

3 つを必ず書く。合わせて 5 行以内。

| 書くこと | 例 |
|---|---|
| 何の作業か | 「請求書 PDF を自動で取り込む機能を作っている」 |
| いまどこか | 「設計が終わり、実装に入る直前」 |
| なぜ止まって聞くのか | 「保存先を 2 案から選ぶ必要があり、運用コストが変わるため」 |

「いまどこか」は**図で見せる**のが最も速い。全体の流れを横に並べ、現在地を強調する (references/diagrams.md の「現在地マップ」)。

### 2. 何を決めてほしい?

問いは 1 文。答え方の種類を明示する。

| 種類 | 問いの形 | 答えの形 |
|---|---|---|
| 承認 | 「この内容で進めてよいか」 | OK / 直してほしい点 |
| 選択 | 「A と B のどちらにするか」 | 案の名前 (+ 条件) |
| 記入 | 「〜の値を教えてほしい」 | 値そのもの |

複数の判断を求めるなら、番号を付けて分け、それぞれに答え方を添える。

### 3. 決めるために何を知ればいい?

判断材料を「読者の疑問」に分解し、1 疑問 = 1 見出しにする。各見出しの中身は次の順:

1. 図か表 (主役)
2. 3 文以内の補足
3. 根拠のラベル (確認済み / 報告のみ / 推測 / 未確認)

### 4. 対象ごとの問い

| 対象 | よく出る問い |
|---|---|
| プラン確認 | 何を作るか / 何を作らないか / 順番 / 所要 / 何が不確か |
| 実装レビュー | 何が変わったか (前後) / 動作確認は / 影響範囲 / 壊れうる所 |
| 設計レビュー | 構成 / データの持ち方 / 他の案との違い / 後から変えられるか |
| 選択 | 各案の後の姿 / コスト / リスク / 戻せるか / おすすめと条件 |
| 調査報告 | 分かったこと / 分からなかったこと / 次にできること |

### 5. 決めたら何が起きる?

答えごとに「次に起きること」を並べる。表にする。

| 答え | 次に起きること | 戻せるか |
|---|---|---|
| OK | 実装に入る。所要 2 日 | 実装前なら戻せる |
| 直す | 指摘を反映して再提示 | — |

### 6. どう答える?

**コピーして返せる**回答例を置く。読者が文章を組み立てなくて済むようにする。

```text
OK。進めてください
```

```text
直してほしい: 保存先は S3 ではなく既存 DB にしてください
```

### 7. 付録

本文から追い出したものを置く。折りたたみでよい。

- 生データ、コマンドと実行結果
- 用語と ID の対応表 (本文で名前に置き換えたもの)
- 対象外にしたこと、未確認のまま残したこと

## 言葉の規則

### 平易な言葉

| 避ける | 使う |
|---|---|
| イミュータブル | 後から書き換えない |
| べき等 | 何回実行しても結果が同じ |
| フォールバック | うまくいかない時の代わり |
| デグレ | 前は動いていたのに壊れる |
| マイグレーション | データの引っ越し |

言い換えが難しい語は、初出で 1 行説明を添える。読者が技術者だと分かっていても、略さない。

### ID ではなく名前

| 避ける | 使う |
|---|---|
| UC-06 | 「結果をスケジューラへ返す」機能 |
| fd678b04 | 「機能フラグを設定する」画面 |
| S3 (ステージ番号) | 「契約を確定する」段階 |
| PR #123 | 「ログイン画面を作り直す」変更 |

名前が長くて何度も出るなら、初出で短い呼び名を定義して使う (例: 以下「返却機能」)。

### テクニカルライティング

- 一文一義。読点でつながないで、文を切る
- 結論を先に、理由を後に
- 主語を省かない。「対応した」ではなく「エージェントが〜を直した」
- 同じものは同じ名前で呼ぶ。表記ゆれをなくす
- 「など」「等」「適宜」を使わない。列挙は列挙し切る
- 数値は表かリストに置く。文中に埋めない
- 段落は 3 文まで、かつ 160 字まで。どちらかを超えたらリストか表にする (検査スクリプトは両方を警告する)

## 表現の選び方

内容の型ごとに、まず図を検討する。図にならなければ表、それでも無理ならリスト。

| 内容の型 | 第 1 候補 | 第 2 候補 |
|---|---|---|
| 作業全体の中の現在地 | 現在地マップ (図) | 手順リスト |
| 手順・流れ | フローチャート (図) | 番号リスト |
| 構成・依存 | 構成図 | 表 |
| 前後の違い | 前後ペア図 | 2 列の表 |
| 案の比較 | 表 | 案カード |
| 位置づけ・トレードオフ | 象限図 | 表 |
| 状態の変化 | 状態遷移図 | 表 |
| 対応関係 (何が何に) | 表 | 対応図 |
| 数量 | 棒グラフ | 表 |
| 条件・例外 | リスト | 表 |

## 完成前チェック

- [ ] 最初の画面で「何の話か」「何を決めるか」が分かる
- [ ] 本文に内部 ID が残っていない
- [ ] 3 文を超える段落が無い
- [ ] 見出し 2 つにつき図が 1 つ以上ある
- [ ] 各主張に根拠ラベルがある
- [ ] コピーして返せる回答例がある
- [ ] 答えごとの「次に起きること」がある
