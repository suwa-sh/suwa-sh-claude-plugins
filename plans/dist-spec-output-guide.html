01

そもそも、何を見直しているのか

distilleryは、要望を要件・設計・詳細仕様へ整えるプラグインです。その中のdist-specは、実装する人へ渡す詳細仕様を作ります。dist-pipelineはこれらの工程を順に進める仕組みです。

問題は、長さだけではありません

一つの貸出登録に、業務説明、画面仕様、APIの型表、データ操作、テスト例、要約ファイルがあります。同じ事実を何度も書くと、変更時に内容がずれます。

反対に、「参照する」「冪等にする」とだけ書いて、具体的な判断を削ると実装できません。

この資料での「実装可能」

仕様と指定された参照先を読むと、入力に対して何が起きるか、失敗したら何が残るか、再送したら何を返すかが決まること。

アプリの実装・運用まで完了したという意味ではありません。

02

何を残し、何を減らすのか

判断基準は、その記述を消したときに、実装者が「結果の異なる選択」をする余地が生まれるかです。

残す判断貸出登録での例書く場所
業務ルール貸出可能な書籍・利用者、貸出期間、予約者との一致条件UC本文
入出力と権限書籍IDなどの必須項目、司書だけが実行可能、成功・失敗の応答API契約
状態と副作用貸出作成・書籍・利用者・予約の更新範囲。途中失敗時の扱い担当するtierの仕様と共有定義
画面の動作入力・結果・再送キーを誰が持つか、いつ再取得するか画面を担当するtierの仕様
受入条件同じ要求を再送しても貸出は1件。競合時は何も更新されない具体的なテスト例

減らせる記述

  • 同じ型・業務ルール・共通UI説明の再掲
  • 通常のレイヤー往復を説明するだけの図
  • 対象のない節、意味の重なるチェック表
  • 契約に影響しない関数名や内部のコード分割の指定

短くしてはいけない判断

  • 計算の基準日、境界値、入力の制約
  • 状態が変わる条件と、変わらない条件
  • 競合・通信断・再送で返す結果
  • 外部送信とデータ保存がずれた場合の回復

一つの事実は、一か所で編集する。
ほかの箇所では、定義のIDと「どこに適用するか」を書きます。ファイル名だけでなく、見出し・操作名・型名まで辿れる参照にします。

03

出力を、役割ごとに分ける

UCは一つの仕事、たとえば「貸出を登録する」です。tierはそれを担当する部分で、画面・API・バックグラウンド処理などを指します。

出力このファイルで決めることほかから参照すること
spec.md
UCの本文		目的、業務ルール、状態変化、業務としての完了条件型・共通部品・担当tierの詳細
tier-*.md
担当部分の仕様		その部分の実行条件、所有者、接続、失敗時の保証UCのルール、API契約、共通UI・DB定義
共有仕様API、DB構造、共通UIなどの共通定義他UCが同じ内容を手書きで複製しない
索引・契約抜粋必要な操作・定義を見つけるための派生物元の定義を自動で取り出す。新しい仕様判断を足さない

第2段階で追加した、契約の自動生成

APIの約束事を記述する標準形式を、OpenAPI、イベントの約束事を記述する標準形式をAsyncAPIと呼びます。契約カタログ方式では、この完全な定義と、各UCが提供・利用する操作を一つの編集元へまとめます。

期待できること

型やエラーを複数の場所で書き直す必要がなくなります。UC別の抜粋には、利用する別UCのAPIや、その型・認証・共通エラーの参照先も含めます。

増える負担と限界

編集元と生成物を管理する仕組みが必要です。生成ファイル自体は増えます。定義の抜け・間違った業務ルールは、自動生成しても直りません。

現在は contract_mode=catalog の明示指定で利用する検証用経路。通常の既定方式は維持しています。対応はOpenAPI 3.1 / AsyncAPI 3.0、参照は同じ文書内の定義を指すパス（ローカルJSON Pointer）に限定。外部参照等は事前に一つへまとめる処理が必要です。

04

貸出登録で見る「短くても決まる仕様」

窓口で書籍を貸し出す操作を考えます。通信が切れると、利用者には失敗に見えても、サーバーでは登録が終わっているかもしれません。そこで、同じ操作の再送を識別する冪等キーを使います。

現サンプルの記載実装者が困る理由改善する内容
キーの保持者がページとフォームの両方に登場送信時と再送時で別のキーを使う恐れAPIを呼ぶページだけがキーと送信本文を保持する
成功後のキャッシュ無効化対象が節ごとに違うどの一覧・詳細を最新にするか決まらない変更される情報から対象を決め、一度だけ定義する
画面でキーを1回生成。同じ画面で次の貸出を開始次の貸出に古いキーを使うと、別内容として拒否される同じ操作の再送と、新しい貸出の開始を区別する
正常テストのキーが idem-0001API契約はUUID形式を要求し、実装が正しければ入力エラーになる正常入力をUUIDへ修正。形式不正は別の異常テストにする

設計例：送信状態を一つの表で決める

ページがキー・送信本文・結果を持ち、フォームは入力と送信通知だけを担当します。以下は改善案であり、現サンプルへの全面適用済み仕様ではありません。

状況キー・本文次に許す動作
初回送信新しいキーと本文を一組で保持送信中は編集・二重送信を止める
通信断で結果不明同じ組を維持同じ要求を再送。別内容へ勝手に変えない
成功を受信結果を確定貸出IDを表示し、変更された情報を再取得
成功後、次の貸出前の結果を解除し、新しいキーを使う同じ画面でも新しい操作を開始できる

これに加え、確定した業務エラー・同一キー別内容の拒否・再読込時の扱いが必要です。詳しい記載例は末尾の根拠資料へ。正常系の表だけで完成と判断しません。

05

文を整理するだけでは解けない不足

5件目は、貸出の保存は成功したが、再送へ返す応答を保存する前に停止したらどうするかです。現サンプルは貸出をDBへ、再送用の応答をKVSへ保存します。この二つが一緒に成功する保証は書かれていません。

「再送で二重登録しない」だけでは足りません。
作成済みの貸出を特定し、同じ成功応答を返せるか。処理中のまま残った記録をどう回復するか。この判断が必要です。

検討する設計と、判断材料

設計の選択肢得られる保証必要な追加・注意点
DBに業務更新と操作結果を一緒に保存
検討の第一候補		貸出と応答の確定を同じトランザクションに含め、再送で結果を取得する操作ID・結果の保存構造、同時要求の排他、保持期限、認証主体との対応が必要。KVSを使うなら補助にする
DB上の操作IDから結果を回復し、KVSを修復KVSに結果がなくても、元の操作と貸出を結びつけて回復する操作IDの永続化と結果再構成が必要。現在状態から当時の応答を再現できるか検証が要る
現状の記載だけで実装を進める通常時の重複抑止は書けても、障害時の結果が決まらない実装可能な仕様としては受け入れない

上の候補は設計提案であり、採用済みではありません。採用時はDB・KVS・API・受入条件を同時に更新します。このHTMLではライブラリ業務の新しい永続化方式を確定していません。

07

何を判断すれば、先へ進めるのか

今決める中心は、ファイル形式の好みではなく、仕様が担保する内容と、その受入基準です。

  1. 内容の修正を優先する。 所有者・操作の区切り・再取得対象・テスト入力を整合させ、障害回復の設計を確定する。
  2. 仕様だけで処理を辿る。 正常処理に加え、失敗・同時要求・結果不明の再送を確認する。結果の異なる判断が残れば修正へ戻す。
  3. 契約カタログは、内容の合格後に既定化を判断する。 型・認可・エラー・依存が抜粋へ残ることと、後段が必要な定義だけで実装できることを確認する。
受け入れる状態

本文と共有参照から動作・失敗結果・テストの期待値が決まる。内部の関数分割など、結果を変えない実装裁量だけが残る。

受け入れない状態

短くなった、図がある、テストが通った、レビューを3回実施したという理由だけで合格にすること。未解決事項の名前を変えても不足は解消しません。

特定モデルでの再生成や、業務アプリ全体の実装は必須条件にしていません。難しい境界は、短い処理表・疑似コード・小さな実行テストで裏付けます。

初めて出てくる言葉

UC / BUC
UCは一つの仕事。BUCは関連するUCをまとめた業務の流れ。例：貸出可否判定と貸出登録。
tier
処理を担当する部分。画面、サーバーAPI、バックグラウンド処理など。
API契約 / schema
プログラム間で受け渡す情報と動作の約束。schemaは項目の型・必須条件・許される値などの定義。
BDD / 受入条件
「この状況で、この操作をすると、この結果になる」という具体例で、満たすべき動作を表す方法。
冪等性 / 冪等キー
同じ操作の再送で副作用を重ねない性質と、その操作を識別する値。新しい操作には新しい値を使う。
トランザクション
複数の更新を、すべて確定するか、すべて取り消すかの一単位にする仕組み。
DB / KVS / キャッシュ
DBはデータの保存先。KVSはキーで値を取得する保存方式。キャッシュは元の情報を一時保持する用途で、同じ意味ではない。
要件対応表 / linked
要件と仕様・テストの対応を示す表。linkedは対応先が実在するという検査結果で、内容の正しさの証明ではない。
UUID
操作などを区別するための識別子の形式。任意の文字列ではなく、決まった形式の値を使います。
lint / CI / CLI
lintは定義の形式・規約の検査。CIは変更時に自動検証する仕組み。CLIは文字のコマンドでツールを操作する方法です。
