# dist-spec 出力簡素化計画

## 目的

実装時に必要な判断・契約・受入条件を保持し、UC ごとの定型説明と重複定義を減らす。
作業ブランチ: `refactor/dist-spec-concise-output`。

## 今回の範囲（第1段階）

1. UC 本文を目的、業務ルール、状態遷移、RDRA 対応、BDD、tier 参照に整理する。
   通常のレイヤー往復図は生成せず、順序・競合・非同期境界を説明する必要がある場合だけ図を使う。
   分岐・計算・バリエーションを業務ルール表にまとめ、ルール本文は一度だけ定義する。
2. Backend / Worker は業務ルール参照と固有の実行条件（原子性、競合、再送、副作用）を記述する。
   DB の型表は統合スキーマに集約し、UC ごとの操作定義は既存の `_model-summary.yaml` に保持する。
   API の入出力・エラー表と `_api-summary.yaml` は維持する。現行 summary は完全な契約ではないため、
   この段階で API 本文を参照だけに置き換えない。
3. Frontend は画面、状態の所有者、データ取得・再取得、イベント、固有の Props バインディングを残す。
   共通コンポーネントの定義・既定値・トークン値の再掲をやめ、ファイルと見出しで特定する。
4. BUC は所属 UC と UC 間の依存・共有定義への参照を残す。単一 UC の BUC に図や空の節を要求しない。
5. 生成・レビュー・トレーサビリティ・実装・Story 生成の指示を同時に更新する。
   省略した図や旧見出しをレビューで復活させない。参照先まで辿って内容の充足を確認する。
6. 貸出登録の縮約例と変更前後の対応表を `samples/distillery/spec-concise/` に追加する。
   既存 pipeline の実行記録は変更しない。縮約例は手編集であることを明示する。

## 維持する契約

- UC / BUC / tier のファイル名、spec-event と summary の既存形式。
- `spec.md` の必須見出し（概要、関連 RDRA モデル、E2E 完了条件、ティア別仕様）。
- UC と各 tier の具体的な Given / When / Then。検証内容が異なるシナリオは残す。
- 情報属性・条件・バリエーション値・状態遷移・外部連携の網羅確認。
- 非同期の配送・再送・重複排除、CLI の入出力・終了コード、design 無しモード。
- events / latest、feedback ledger、モデル選定、並列実行方式。

## 第2段階（別変更）

API / AsyncAPI の完全な定義元と統合契約の生成方式を決定し、summary を索引または機械生成物にする。
契約の型・制約・認可・エラー・依存を欠落なく統合できる検証を先に用意してから、API 本文の項目表を削る。
BUC / traceability の決定的生成や、参照先だけを取り出す read-set 自動化もこの段階で扱う。

### 第2段階の実装方式

- `_cross-cutting/api/contracts.json` を編集可能な契約カタログとする。
  OpenAPI 3.1 / AsyncAPI 3.0 の完全な定義と、UCごとの提供/利用operationの対応を保持する。
  型・認可・エラー・拡張フィールドを独自summary形式へ翻訳せず保持する。
- 統合契約、UCの `_api-summary.yaml`、依存先まで含む `_contract-slice.json` を決定的に生成する。
  UC本文はoperation IDと固有の実行条件だけにする。旧summary形式は既存サンプル用に維持する。
- カタログは単一の担当が更新する。UC生成担当は派生物を編集せず、不足をカタログへの変更要求にする。
- 参照切れ、operation重複、所有者欠落、未知operationへの依存はエラーとする。標準仕様のlintは別途必須。
- BUCはカタログの所属と呼出依存から生成する。トレーサビリティはRDRAの要素一覧を分母とし、
  UCの機械可読な対応記録と照合する。リンクの実在と意味上の充足は別の判定として報告する。
- 抜粋を実装入力へ追加する際は、そのcontent hashもinput-manifestへ追加する。
- 実装可能性の受入確認が通るまではカタログ方式を明示的に選ぶ検証用経路とする。旧イベントを自動移行しない。

## 完了基準の修正（ユーザーの意図の再確認）

目的は特定モデルの出力再現ではなく、過不足なく実装できる出力仕様。
実装者が本文と共有参照だけから正常・失敗・競合・再送の結果を決められることを基準にする。
内部の関数分割等は実装裁量として残し、結果を変える業務判断・矛盾・未宣言依存を残さない。
型検証・BDD保持・リンク実在・削減率は補助検証であり、受入判定を代替しない。

貸出登録の再評価は `samples/distillery/spec-concise/implementation-review.md`。
キー所有者・キャッシュ対象の矛盾、操作ごとのキー更新、BDDのUUID違反、DB/KVS間の障害回復不足を検出。
旧比較例は変更前の情報保持を測った資料として保存し、完成仕様と評価しない。
共通の生成/レビュー基準と、短くても挙動を決められる記載例を追加した。
